## 一、教师模型与蒸馏(训练细节)

### Q21｜文本的"教师"到底是什么?是外部模型吗?

**首答:** 不是外部模型。我们的教师是**上一代自己的提交分数** —— 每一代伪标签都由当时最好的一版提交,经排名归一化后转成软标签,再喂给学生。所以这是一条**迭代自举**链路,而不是引入第三方模型。

**展开:** 构造脚本是 `code/fusion/mk_pseudo*.py`,输入是那一代的提交 CSV,输出 `runs/pseudo_best*.npy`。这带来两个必须承认的性质:其一,教师与学生的能力上限绑定,不会凭空超过自有模型;其二,属闭环自训练,存在偏置累积风险 —— 这也是为什么官方真标签要单独加权锚定(见 Q27)。

**后台依据:** `mk_pseudo_v2.py`;`runs/pseudo_best*.npy`;`p43`运行日志中的 `labels = pseudo_best_v2`。

### Q22｜伪标签一共做了几代?最终 14B 用的是哪一代?

**首答:** 一共四代,分别对应四次提交成绩:**v1 ← 0.973656;v2 ← 0.978284;v3 ← 0.980896;v4 ← 三代 14B 集成**。最终交付的 14B p4 谱系用的是 **v2**。

**展开:** 代次并非越大越好 —— v3、v4 是后续探索,最终选型以目标域实际表现为准。适配器目录里的 `meta.json` 写明 `labels = pseudo_best_v3` 的属于第三轮(谱系名 `r3` 的来由),写明 `pseudo_best_v2` 的属于第二轮;`rN` 的 N 与伪标签代次一致,可逐项核对。

**后台依据:** `runs_full_backup/lora7b_distill_r3{a,b}_fold{0..4}_adapter/meta.json`;`p43_14b_p2.py` 默认标签路径。

### Q23｜0.978284 那个"多分支融合(教师)"内部是什么结构?

**首答:** 它是一次**家族级加权**:约 `0.15 × 微调分类器 + 0.10 × 语言模型内部特征 + 0.45 × 1.5B 蒸馏学生 + 0.30 × 7B 蒸馏学生`。也就是说,这一版的主力(45%)并不是 14B,而是被 14B **蒸馏出来的 1.5B 学生**。

**展开:** 家族内部还有一层 —— 微调族 `= 0.60 × 1.5B蒸馏 + 0.10 × 14B官方 + 0.20 × 7B蒸馏 + 0.10 × 7B官方`;语言特征族 `= 0.25 × qwen_pair + 0.25 × q4b_hidden_last + 0.50 × q4b_hidden_mean`。要特别注意:**第 ① 行(0.978284)与第 ④ 行(0.981069)分属不同代际的教师配置**,不能混称为同一个"教师"。

**后台依据:** `v2_p2peak.py` 原始 docstring;`p4_report.json`。

### Q24｜七B 和 1.5B 这些学生,具体是怎么从 14B 蒸馏出来的?

**首答:** 学生是 Qwen2.5-7B-Instruct(或 1.5B),教师是 Qwen2.5-14B-Instruct。训练集 = **官方 1000 条硬标签 + 20000 条软标签**,损失是**逐样本加权的 BCE** —— 硬标签权重 4.0,软标签权重乘置信度。学生挂 LoRA 训练,冻结基座。

**展开(完整超参,来自 `p32_distill.py` / `p32_old_retrain.py`):**

| 项 | 值 |
|---|---|
| 损失 | `BCEWithLogitsLoss(reduction="none")` → `loss = (逐样本损失 × 该样本权重).mean()`(**不除以权重和**) |
| 官方硬标签权重 | **4.0** |
| 软标签权重 | `conf = clip(4·|soft − 0.5|, 0, 1)` |
| 优化器 | **AdamW**,`weight_decay = 0.01` |
| 学习率 | **5e-5**(7B)/ **1e-4**(1.5B) |
| epoch | **1** |
| batch | **4**(7B)/ **8**(1.5B) |
| LoRA | `r=16, lora_alpha=32, lora_dropout=0.05`,`target_modules = q/k/v/o_proj` |
| 推理 | 取 `logits[:,1] − logits[:,0]` 的 logit 差(与训练用的 `logits[:,0]` 单调等价,排序不变) |

**后台依据:** `p32_distill.py:138,145,152,157`;`p32_old_retrain.py:155,162,171,176`。

### Q25｜图像的教师是谁?"转导蒸馏"具体怎么训?

**首答:** 图像教师是一个**混合分数线**:`anchor = 0.70 × rank(cliph50) + 0.30 × rank(siglip030)`,当时榜上 0.900099。它给两万张测试图打分,分数转排名后作软标签;学生是 CLIP ViT-H-14,冻结骨干只训 LoRA。

**展开:** 教师共两代 —— 第一代 `anchor`(0.900099)训出 `cliph_rerun`;第二代更强的混合(0.914498)用于 `train_distill2.py`。训练集 **21000 = 20000 软 + 1000 硬(权重 4.0)**,折内 800 训 / 200 验。学生侧:`CLIP ViT-H-14 冻结`,`LoRA r=32 α=32 dropout 0.05`,可训参数 **15.73M(约 2.5%)**;`AdamW, weight_decay=0.01, LR=1e-4, BS=32, bf16`;**主跑 2 epoch,三个种子各 4 epoch**。需要说明:anchor 的 CLIP-H 侧脚本与权重已丢失,只能复现到相关系数 0.96,但它的分数 CSV 仍在,**"用它当教师"这一步是可复现的**。

**后台依据:** `train_distill2.py:70,71,188,265`;图像 `docs/08_分量溯源与种子明细.md`。

## 二、最终模型:完整训练配置

### Q26｜文本最终模型(14B p4)的完整配置是什么?

**首答:** 五折,每折 800 条官方样例训练、200 条验证,同时**全量使用 20000 条无标签目标文本**;LoRA 挂 q/k/v/o_proj,AdamW 学习率 5e-5、权重衰减 0.01,训练 2 个 epoch,bf16,输入截断 512 tokens。

**展开(来自 `p43_14b_p2.py`):**

| 项 | 值 |
|---|---|
| 基座 | Qwen2.5-14B-Instruct(冻结) |
| LoRA | `r=16, lora_alpha=32, lora_dropout=0.05`,`q/k/v/o_proj` |
| 每折数据 | 官方 800 训 / 200 验 + 20000 全量软标签 |
| 官方硬标签权重 | **2.0** |
| 软标签权重 | `conf = clip(4·|soft − 0.5|, 0, 1)` |
| 损失 | 逐样本 `BCE × 权重` 后取 `mean`(不除权重和) |
| 优化器 | **AdamW**,`lr = 5e-5`,`weight_decay = 0.01` |
| epoch | **2** |
| 精度 / 长度 | bf16 / 512 tokens |

**后台依据:** `p43_14b_p2.py:82,107,133,150,155`;`p42_self_train.py` 同族默认 2 epoch。

### Q27｜硬标签权重到底是 2 还是 4?

**首答:** **都出现过,取决于脚本** —— 14B 自训练谱系用 **2.0**;7B 与 1.5B 的**蒸馏学生用 4.0**。原因是蒸馏学生以拟合教师软标签为主,更需要真标签把方向锚住,所以真标签相对权重更高。

**展开:** 这条我们**主动更正**:早期材料统一写 2.0 是**不完整**的。`p42_self_train.py:134` 与 `p43_14b_p2.py:133` 写 2.0;`p32_distill.py:138` 与 `p32_old_retrain.py:155` 写 4.0。由于最终融合里 7B 占 10%,这个差别会进入成绩,必须区分。另外要说明:**加权只能减轻伪标签错误的影响,不能保证它不被传播。**

**后台依据:** 上述四处源码行;答辩材料报告 §2.3 的同名说明。

### Q28｜图像八个分量的训练配置一览?

**首答:** 八个分量共享三个骨干,各自只挂 LoRA 与分类头。四个 CLIP-H 是转导蒸馏,另外四个是纯监督(GenImage++ 78k 与 Tiny-GenImage 28.8k),`(r, α)` 逐分量不同。

**展开:**

| 分量 | 骨干 / 输入 | 监督 | 训练数据 | r | α |
|---|---|---|---|---|---|
| `img_cliph_rerun` | CLIP ViT-H-14 @224 | 转导蒸馏 | 20000 软 + 1000 硬(w=4) | 32 | 32 |
| `img_cliph_s20261101/02/03` | 同上 | 转导蒸馏 | 同上(仅换种子) | 32 | 32 |
| `img_gpp_siglip2` | SigLIP2-so400m-384 | 纯监督 | GenImage++ 78k | 16 | 32 |
| `img_bigg_rerun2` / `_rerun3` | CLIP ViT-bigG-14 @224 | 纯监督 | Tiny-GenImage 28.8k | 16 | 32 |
| `img_bigg_s384_retrain` | CLIP ViT-bigG-14 @384 | 纯监督 | Tiny-GenImage 28.8k | 32 | 64 |

注:`α = r` 时缩放系数 1.0,`α = 2r` 时 2.0 —— **不能统一说"缩放都一样"**。

**后台依据:** `src/image.py` 与 `app/models.py` 的分量配置;图像 `docs/08`。

### Q29｜数据增强具体做了什么?

**首答:** 图像侧是 **JPEG 压缩 + 水平翻转**;文本侧做过**改写增强** —— 用 Qwen3-1.7B 对文本做润色、改写、压缩(保留原标签),单批 600 条、总量约 3000 条,并对官方样例**4 倍过采样**以维持配比。

**展开:** 必须说明两点:① 文本改写属**训练机制层面的探索**,在留存的教师配置里,**含改写数据的分支权重为 0**,所以它没有进入最终成绩;② 我们**未做攻击前后的对照评测**,因此**不能把这些增强说成"已证明的鲁棒性收益"**。图像的 JPEG 与翻转同理,属设计应对而非已验证结论。

**后台依据:** 图像增强代码;文本改写分支配置与 `p4_report.json`(该分支权重 0)。

### Q30｜一共用了哪些数据集?各多少条?

**首答:** 官方标注 1000 条(正负各 500),复赛无标签目标集 20000 条;外部数据只用在纯监督分量与基线分支上 —— GenImage++ 78k、Tiny-GenImage 28.8k、中文 HC3 23762 条与 Qwen 合成 1497 条(合计 25259)。

**展开:** 分布是:图像的 4 个转导分量用**官方 1000 + 目标集 20000**;4 个纯监督分量分别用 GenImage++ 与 Tiny-GenImage;文本的 robust 分支用**官方 1000 + 外部 25259**;两路带权的 7B 微调分支**只用官方 1000,不含伪标签与外部数据**。另外做过 302k 规模的失败探索(见原 Q11),那是 25% 进度的诊断值,不能作为结论。

**后台依据:** 两赛道训练脚本与 `p4_report.json`;图像 `docs/05`。

### Q31｜为什么文本是 9:1,而不是别的比例?

**首答:** 因为主力是 14B —— 它单独就有 0.981069,7B 是**辅助补盲**的角色。0.9/0.1 是候选配置里表现最好的一个,增益本身很小(**+0.000232**),我们如实按目标域表现选择,不把"集成"说成必然更优。

**展开:** 反例就在同一份材料里:**双 14B 种子集成 0.980896 低于 14B p4 五折的 0.981069** —— 说明加分量不保证提升。所以 9:1 是**选型结果**,不是通用最优比例;换数据分布或换基座都应重新搜。

**后台依据:** `p101_verify_7b2.py`;`submit_p4_90_7b2_10.csv` 的构成核对。

## 三、名词与符号(被问到"这个词/这个符号什么意思"时)

### Q32｜"异构表征"是什么意思?

**首答:** 指**让多种来源不同的表征各自出分,再在分数空间融合**,而不是把特征拼在一起训一个模型。图像侧是 3 类骨干 × 224/384 两种输入尺度 × 转导蒸馏与纯监督两种训练方式;文本侧是 14B 与 7B 两个规模,教师里还包含 LightGBM 这类树模型和冻结表征探针。

**展开:** 动机是不同骨干对同一扰动的敏感方向不同、犯错不相关。我们的数据支持这点:**同配方换种子的相关(CLIP-H 四路 0.960089)明显高于跨架构相关(↔SigLIP2 0.7914、↔bigG384 0.7091)**。但两个限定必须讲清:① 融合发生在**分数/秩空间**,不是特征级融合;② "异构"是**设计动机**,其增益**未经受控消融与显著性检验**,且"互补 ≠ 必然提升"。

**后台依据:** 图像 `docs/08` 相关系数;答辩报告 §4 方法学结论。

### Q33｜那张秩相关系数 ρ 的图有什么用?

**首答:** 它不是成绩,是**诊断** —— 用来回答"八个分量会不会是重复的、融合有没有意义"。它同时给两个设计决策提供了依据。

**展开:**
1. **定分槽规则**:同配方只换种子的 CLIP-H 四路 ρ≈0.96(几乎是同一个模型)→ 放**同一槽内平均**降方差;跨架构(0.79 / 0.71)明显更低 → 携带新信息 → **单独成槽、单独给权**。`5:2:1` 的槽划分就是这么定的。
2. **定先验权重**:尺寸先验与模型分数相关仅 **0.146** → 近乎独立,才有资格占 20%;若相关 0.9,给 20% 就是重复计分。
3. **诊断转导代价**:掺软标签的分量彼此 ρ=**0.9315**,而纯监督之间只有 0.8012 / 0.7785 —— 说明**转导蒸馏会让分量趋同、削弱互补性**。

**后台依据:** 分量 CSV 复算;图像 `docs/08`。**注意**:ρ 低是互补"潜力",不等于融合必然提升。

### Q34｜公式里的 m_H、m_B、m_384 和 prior 是什么?

**首答:** `m_H / m_B / m_384` 是**槽内平均值** —— 而且参与平均的已经是各分量的 ECDF 百分位,不是原始分数;`prior` 是**尺寸先验的百分位**,只用图片规格算出。整条融合链每一步都在 0~1 的百分位空间里。

**展开:** `m_H` = 主槽 5 个成员(4 个 CLIP-H + SigLIP2)百分位的等权平均;`m_B` = bigG@224 槽两个分量的平均;`m_384` 槽只有 1 个分量,所以直接等于它。`prior` 的内部是**分辨率桶查表与梯度提升树按 0.4 / 0.6 混合后再取一次 ECDF**,所以它本身已是 0~1 百分位,才能与 `base` 按 0.8 / 0.2 相加 —— **"同量纲"是这一步能成立的前提**。

**后台依据:** `app/fusion.py`;`prior_meta.json`、`bucket.json`。

### Q35｜"离线/在线"是指断网吗?(术语坑)

**首答:** 不是。本方案里的"离线/在线"指**批处理 vs 逐条实时**,不是"断网 vs 联网" —— 恰恰相反,**两个镜像运行期都是完全离线的**,不访问任何外部网络。为避免歧义,我们口播时改说**"批量提交链路"与"镜像服务链路"**。

**展开:** 批量链路一次拿到全部 20000 条,可以用全局排名,产出提交 CSV(复赛成绩来源);镜像服务一次只收到一条,只能用当前输入,所以必须把全局排名改写成逐图可算的形式(见 Q07)。两条链路排序相关约 0.99987,但由于平均与 sigmoid 不可交换,不能保证完全一致。

**后台依据:** `app/fusion.py` 与 `server_dual_v4.py` 的两条路径;一致性分析脚本。

### Q36｜512 tokens 截断是怎么回事?

**首答:** 文本在**推理阶段显式截断到 512 tokens**(只保留头部)。这是**统一的长度上限**,不是对长文本做过滑窗。因此超长文本的尾部线索会丢失 —— 这是已知限制。

**展开:** 这样做是为了控制显存与延迟可预测性:注意力开销随长度增长,固定上限让单条延迟稳定,从而支撑逐条 HTTP 服务。改进方向是**滑窗分段后再聚合**,但当前**没有做这件事,也没有相应收益实验**。回答时应说明:这个上限不是赛题要求,是我们的工程选择。

**后台依据:** `server_dual_v4.py` 分词段明确启用 `truncation`,上限 512。

### Q37｜p4、r3a、r3b、a/b 这些名字怎么读?

**首答:** `p4` 是 14B 侧的训练谱系名(脚本 `p42/p43` 一族);`r3` 表示**第 3 轮蒸馏**(适配器 `meta.json` 写明 `labels = pseudo_best_v3`);`a` / `b` 是**同一轮的两个随机种子**。所以"`r3a` 五折 ∪ `r3b` 五折"就是**两个种子各五折**,合计 10 个适配器。

**展开:** 同族的 `lora7b_distill_r2` 即第 2 轮 —— `rN` 的 N 与伪标签代次一致,这是可核对的。要强调:**15 个适配器 = 14B 五折 5 个 + 7B 两谱系各五折 10 个**,是"两个基座、三条谱系",**不是十五折或十折交叉验证**。

**后台依据:** 各适配器目录 `meta.json`;`p101_verify_7b2.py` 的集成定义。

### Q38｜"43"到底指几个?(两个 43 别混)

**首答:** 是两件不同的事:**图像侧的 43 = 官方 1000 张里出现的 43 个不同分辨率(43 个桶)**;**文本侧的 43 = 教师候选信号池的 43 路候选**。数值相同纯属巧合。

**展开:** 图像那 43 个桶用于尺寸先验:每桶存标签均值,并按 `(均值×n + 全局均值×5)/(n+5)` 做收缩平滑。文本那 43 路里,**实际带权的只有 6 路**,其余权重为 0。

**后台依据:** `bucket.json`;`p4_report.json` 的候选池与有效权重。

### Q39｜rank01、σ、logit、ECDF 之间是什么关系?

**首答:** 它们解决的是"不同模型的输出不可比"这一个问题,出现在链条的不同位置:`logit` 是模型原始输出;`σ`(sigmoid)把 logit 压到 0~1,但**它依赖绝对值,不能解决跨模型可比性**;`rank01 / ECDF` 把分数换成**名次百分位**,与 AUC 天然一致、免疫未校准和极端值。所以**离线融合在秩空间做**,在线服务在 logit/概率空间做。

**展开:** 关键细节:`σ` 与"取平均"**不可交换** —— 先平均 logit 再 `σ` ≠ 先 `σ` 再平均,这正是两条链路排序略有差异的结构性原因。另外 `rank01` 与 `ECDF` **数值完全相等**(实测最大绝对差为 0),区别只在工程实现:ECDF 可预存成查找表,从而**单张也能算**。

**后台依据:** `app/fusion.py`;`p97_p4_7b_sweep.py`;一致性分析。

### Q40｜什么是 SPAI?

**首答:** SPAI 是历史基线名称(`baycup_v28_cliph50_siglip030`)里的一部分,**仓库里没有留存它的定义**,我们按原名引用,不额外解释它的含义。

**展开:** 态度上宁可承认"这是历史资产、当前无法完整溯源",也不给它编一个看起来合理的展开。同理,anchor 的 CLIP-H 侧脚本已丢失,复现只能到相关系数 0.96;但它的分数 CSV 仍在,**用它当教师这一步是可复现的**。

**后台依据:** 图像历史基线目录与 `docs/07`。

### Q41｜五折是怎么做的?为什么不是十折?

**首答:** 官方 1000 条按五折划分,每折 800 训 / 200 验。文本最终是**三组五折**(14B 一组 + 7B 两个种子各一组)共 15 个适配器 —— 这是**三个"五折"并列**,不是十折或十五折交叉验证。

**展开:** 每组五折内部,验证样本对该折模型是"没见过的"(即 OOF),因此可用于权重搜索;但要注意:**在同一批 OOF 上搜索融合权重,仍可能产生选型偏差**,所以最终取舍以官方复赛反馈为准。图像侧同样五折,但 CLIP-H 用全部 1000 张训练、不做 80/20 划分,bigG 的两个种子才改变划分 —— 这一点不能含糊。

**后台依据:** 两赛道训练脚本的折划分;图像 `docs/08`。

### Q42｜OOF 是什么?用它搜权重有什么风险?

**首答:** OOF 指"每条样本的预测来自没见过它的那一折模型"。它让 1000 条官方样例都能当验证用,是标注稀缺时的常规做法。风险是:**在同一份 OOF 上反复搜索融合权重,等于把验证集当训练集用**,可能高估。

**展开:** 我们对此的处理是:OOF 只用于**选择方向**(比如 0.9/0.1),最终方案取舍**以官方复赛反馈为准**;并在材料里明确"未做严格的控制变量消融与显著性检验"。被追问"你们的权重是不是过拟合出来的"时,应承认这个风险,而不是否认。

**后台依据:** 折内验证逻辑;答辩报告 §2.4 的如实说明。

## 四、追问预案(原 20 问未覆盖的角度)

### Q43｜批量提交的成本是多少?为什么不能用单条延迟乘条数?

**首答:** 批量链路**远快于**"单条延迟 × 条数"。给出可比的摊销值:文本约 **0.09 ~ 0.14 秒/条**(由整段 30~45 分钟摊到 20000 条),图像约 **0.07 秒/张**(8 个分量合计,由单分量实测 118 张/秒外推)。对比服务链路的 0.68 秒/条与 0.236 秒/张,批量约为其 1/5 ~ 1/7.6 与 1/3.3。

**展开:** 三个必须说明的口径:① **不能互推** —— 批量无 HTTP、无逐条适配器切换、无推理锁,单条延迟里的固定开销在批量里只付一次;② 文本那个数**是上界**(整段含 OOF 预测、评估与保存,且当时批大小仅 2~16、GPU 与租户共享);③ 图像 0.07 秒**是外推**(只有单分量实测,见下)。所以我们口播只说"批量是整批链路,单条成本远低于服务延迟",要数字就给摊销值。

**后台依据:** 训练/预测日志的时间戳差;图像分量进度日志 `replay 10408/20000 用 88 秒`(≈118 张/秒)。

### Q44｜0.981301 与"综合得分 90.1337"是什么关系?

**首答:** 0.981301 / 0.918887 是两条赛道的**复赛 AUC**;综合得分是把两个 AUC 代进赛会计分式 `e^(4×AUC_image) + e^(4×AUC_text)` 得到的 **90.1337**。它不是准确率,也不是两个 AUC 的平均。

**展开:** 讲的时候要说清"我们提交的是 AUC,综合分是按赛会计分式算出来的",避免让评委以为 90 是另一个独立指标。另外两个 AUC 都是在**离线批量链路**上得到的,不等于镜像服务链路自身的成绩(见原 Q08)。

**后台依据:** 提交记录与赛会计分式;答辩报告 §1.1。

### Q45｜训练一共花了多少算力?

**首答:** 单卡 RTX 4090(24 GB)。文本侧每折 1~2 个 epoch,单折训练到结束约 **30~45 分钟**(含预测与评估);图像侧主跑 2 epoch、种子各 4 epoch。全部实验在单卡上串行完成,没有多机。

**展开:** 需要如实说明:许多早期探索(302k 规模等)受**训练预算限制**,因此那些失败结果**不能作为"更多数据有害"的结论**。可复现的最小集合是留存的脚本与配置,而不是全部试错过程。

**后台依据:** 训练日志时间戳;图像 `docs/05`。

### Q46｜如果重做一次,你们会先改什么?

**首答:** 三件事,按优先级:① **把"提交链路与交付链路的一致性"在方案设计早期就定下来**(这决定融合能不能用全局排名);② **控制变量做消融** —— 固定基座、预算和种子,只改一个设计点,并对小幅增益做配对置信区间;③ **先做分组评测**(生成来源 / 后处理 / 长度 / 领域),再决定优化方向。

**展开:** 这三条对应的都是我们已经踩过的坑:一致性约束让图像不得不改写 ECDF、让文本退化到 sigmoid;没有消融导致 0.0015 的增益说不清归因;没有分组评测导致"鲁棒性"只能停在机制层面。

**后台依据:** 答辩报告 §4、§5 的方法学结论与已知局限。

### Q47｜为什么不做端到端多模态?为什么不上更大的模型?

**首答:** 因为**赛题是两条独立赛道、分别评价**,联合建模不会带来额外分数,反而增加风险与算力。更大模型方面:14B 在 bf16 下权重约 28 GB,已经要求 ≥48 GB 显存;上更大模型会直接冲击交付标准与单条延迟。我们选择把预算花在**目标域软监督**上 —— 它带来的提升(0.978284 → 0.981069)比单纯换更大基座更确定。

**展开:** 这不是说更大模型没用,而是**在本赛题约束下边际收益低**:交付有 90 秒单条上限、300 秒启动上限,而我们的文本启动已用掉 70.1 秒。如果算力与显存不受限,值得试的是更强基座 + 蒸馏,但那需要重新做全套验证。

**后台依据:** 交付标准 v1.2;文本镜像体积与显存实测。

### Q48｜误报率、漏报率具体是多少?

**首答:** **我们没有这两个数字**,因为我们没有业务侧的标注数据来定义"误报"。AUC 只衡量整体排序能力,不能直接换算成某个阈值下的误报/漏报。要用到审核,必须先在代表性业务数据上确定可接受的误报率,**再反推阈值**、测对应的召回。

**展开:** 这是方案的已知缺口之一,也是下一阶段优先级最高的实验之一。回答时不要给任何拍脑袋的误报率 —— 那比承认没有更危险。

**后台依据:** 答辩报告 §5 已知局限;原 Q09、Q19。

### Q49｜分数 0.9 是不是"90% 概率是 AI 生成"?

**首答:** **不是**。输出是**未经概率校准**的连续置信度,适宜做排序和阈值筛选,不能解释为"AI 生成的概率"。两个原因:① 融合是在秩空间完成的,分数承载的是**相对位置**;② 我们没有做过概率校准(如 Platt / isotonic),也没有校准所需的业务标注。

**展开:** 如果业务需要概率语义,做法是:先用代表性数据做校准,再报告校准后的 ECE 或可靠性曲线。当前只能承诺"排序可用",不能承诺"概率可解释"。

**后台依据:** 接口协议说明;答辩报告附录的输出值说明。

### Q50｜你们的方案有什么是不可替代的?

**首答:** 三件事,都能落到具体实现:① **把批排名改写成逐图可算的 ECDF 形式** —— 实测与批 rank **数值完全一致**(8 个分量逐个比较,最大绝对差均为 0),这解决了"评价要全局排名、交付要逐条调用"的结构性矛盾;② **目标域软监督的完整链路**(自举伪标签 + 置信度加权 + 真标签锚定),并用官方反馈逐代验证;③ **对自身边界的如实披露** —— 转导代价、尺寸先验的快捷学习性质、未做的消融与鲁棒性评测,我们都写在材料里。

**展开:** 我们不声称首创 LoRA、自蒸馏或秩融合 —— 这些是通用技术。我们的贡献是**在交付约束下把它们组织成一条可复现、可核对的链路**,并把不确定性标注清楚。如果评委追问"哪一条最硬",答案是第 ① 条:它有一个可验证的等式,而不是一个说法。

**后台依据:** `app/fusion.py` 与分量对照脚本;答辩报告 §3.3。
