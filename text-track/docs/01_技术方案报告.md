## 二、任务理解与关键挑战

| 挑战 | 我们的观察 |
|---|---|
| **域偏移** | 官方样例集(1000 条)与复赛测试集(20000 条,改写强度更高)分布差异显著 —— 直接用样例训练的模型在复赛上明显退化 |
| **改写对抗** | 复赛数据包含人工润色、多模型混合改写,基于表面统计特征(困惑度、token 概率)的检测器性能大幅下降 |
| **无标签目标域** | 复赛测试集无标签,无法直接监督训练 |
| **评估噪声** | 官方样例仅 1000 条,五折后每折仅 200 条验证样本,AUC 统计噪声约 ±0.01,不足以做模型选择 |

**核心结论**:官方样例上的验证分数**不能预测复赛表现**,唯一可靠的信号是复赛反馈。

## 三、技术路线

### 3.1 整体框架

```
┌─────────────────────────────────────────────────────────────┐
│ 第一轮:官方样例监督训练                                       │
│   官方 1000 条 → LoRA 微调(Qwen2.5-7B/14B)                   │
│   + 多视角特征分支(LLM 似然、隐藏态、外部数据)                 │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 第二轮:多分支融合 + 伪标签自训练                              │
│   48 个异构分支 rank 融合(0.978284)                          │
│   → 对复赛 20000 条生成软伪标签                                │
│   → 训练 14B 学生(域自适应)                                   │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 第三轮:多随机种子自训练 + 异构集成                            │
│   同一强伪标签下训练多个 14B seed                              │
│   → 复赛反馈选择最优组合                                       │
│   → 最终 0.90 × 14B(p4 五折) + 0.10 × 7B(r3a/r3b 十折)      │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 伪标签构造(核心)

对融合后的复赛预测分数 `s`(20000 条),构造软标签与置信度权重:

```python
rank = rank01(s)                              # 排名归一化到 (0,1)
soft = sigmoid(4 × (rank − 0.5))              # 软标签,范围 (0.08, 0.92)
conf = clip(4 × |soft − 0.5|, 0, 1)           # 置信度权重
```

**训练样本构成**(每折):

| 数据 | 数量 | 标签 | 损失权重 |
|---|---|---|---|
| 官方训练折 | 800 | **真实硬标签** | **2.0** |
| 复赛测试集 | **20000** | **软伪标签** | `conf` |

**关键设计**:官方真标签权重加倍,保证模型不被伪标签带偏;复赛数据每折全量参与,实现域对齐。

### 3.3 模型与训练配置

| 项 | 配置 |
|---|---|
| 基座 | Qwen2.5-14B-Instruct / Qwen2.5-7B-Instruct |
| 微调方式 | LoRA:r=16, α=32, dropout=0.05,target = q/k/v/o_proj |
| 分类头 | `score`(2 类,新初始化) |
| 损失 | `BCEWithLogitsLoss(logits[:,0], target) × weight` |
| 优化器 | AdamW,lr=5e-5,weight_decay=0.01,linear warmup 10% |
| 训练 | 2 epochs,seq_len=512,batch=2 |
| 交叉验证 | 官方 1000 条 5 折;复赛数据不参与验证 |
| 预测 | `logits[:,0]`(AI 方向);方向保护:AUC<0.5 自动翻转 |

**为何用 `logits[:,0]` 而非 softmax**:早期版本使用 `softmax(logits)[:,1]`,导致 **45% 的样本并列在 1.0**
(数值饱和),排序信息大量丢失。改用 logit 原值后,`frac==max` 从 **49.5% 降至 0.10%**。

### 3.4 关键实验结果(基于复赛反馈)

> **本表是递进消融实验记录**,用于说明每一步的增益来源。
> **最终提交的方案是最后一行,复赛文本 AUC = 0.981301**;表中其余数值均为中间实验结果,非提交成绩。

| # | 实验 | 复赛 AUC | 相对上一行的增益 |
|---|---|---|---|
| 1 | 纯 14B seed1 监督微调 | 0.9615 | 单分支基线 |
| 2 | 48 分支融合(含 LLM 似然/隐藏态) | 0.978284 | +0.0168 |
| 3 | 第一轮自训练(14B seed1) | 0.979964 | 域自适应 **+0.0017** |
| 4 | 双 seed 集成(seed1+seed2) | 0.980896 | 多 seed **+0.0009** |
| 5 | 纯 seed2(最优单一模型,中间结果) | 0.981069 | seed 间差异达 0.0011 |
| 6 | **★ 最终提交方案:0.90×14B(p4 五折)+ 0.10×7B(r3a/r3b 十折)** | **0.981301** | **异构混合 +0.0002** |

**最终提交成绩:0.981301(复赛文本榜第 4 名)。**

**重要发现**:

1. **迭代自训练有效**:用融合模型对无标签目标域打软标签,可显著提升复赛表现(+0.0017)
2. **多随机种子集成有效**:同配置不同种子的模型集成可稳定提升(+0.0009)
3. **异构混合优于同构混合**:14B 与 7B 的集成(相关 0.995)优于两个 14B 种子(相关 0.996)
4. **伪标签的"信息多样性"比"分数"更重要**:用 48 分支融合(0.9783)训练的模型,优于用纯 14B 集成(0.9809)训练的模型

## 四、最终提交方案(0.981301)

### 4.1 模型构成

```
score = 0.90 × sigmoid( mean_{fold=0..4}  logits[:,0] )      ← Qwen2.5-14B + p4 LoRA(5 折)
      + 0.10 × sigmoid( mean_{fold=0..9}  logits[:,0] )      ← Qwen2.5-7B + r3a/r3b LoRA(10 折)
```

- 14B 侧:p4 五折 LoRA 的 logit 均值 → sigmoid
- 7B 侧:r3a 五折 + r3b 五折,共 10 个 adapter 的 logit 均值 → sigmoid
- 两侧按 **0.90 / 0.10** 做分数级融合

### 4.2 为什么线上用 sigmoid 而不是 rank

离线方案使用 **rank01 融合**,但评测平台**逐条下发请求**,服务端拿不到全量分布、无法做排名归一化。
因此线上改用 **sigmoid 分数级融合**。经 20000 条复赛数据验证,两种方式的排序相关性达 **0.999997**,
排序差异 >0.01 的样本占比仅 **0.065%**,**AUC 预期不变**。

### 4.3 推理流程

```
POST /predict {req_id, data}
    ↓
① 14B 侧:依次切 5 折 LoRA adapter,前向取 logits[:,0],平均
② 7B 侧:依次切 10 折 LoRA adapter(a7_0..4 + b7_0..4),前向取 logits[:,0],平均
③ 各自 sigmoid → p14, p7
④ score = 0.90 × p14 + 0.10 × p7,裁剪到 [0,1]
⑤ 返回 {req_id, code:0, score}
```

### 5.3 构建过程中定位并解决的关键问题

| # | 问题 | 现象 | 解决 |
|---|---|---|---|
| 1 | **依赖闭包不完整** | 构建阶段仅解包了 10 个直接依赖,119 个传递依赖(numpy、sympy、networkx、`nvidia-*`、triton 等)缺失 | 重新解析并落盘完整闭包(57 个 wheel) |
| 2 | **Python ABI 错配** | 主层里 torch/scipy/tokenizers/sentencepiece/functorch 共 **124 个 `.so` 是 cpython-312 产物**,而镜像是 Python 3.10,`import torch` 报 *Failed to load PyTorch C extensions* | 全部替换为 cp310 版本(依赖层覆盖) |
| 3 | **HEALTHCHECK 依赖不存在的命令** | `python:3.10-slim` 内没有 `curl`,原 `HEALTHCHECK ... curl -f ...` 会让容器恒为 unhealthy | 改为等价的 Python 标准库实现 `healthcheck.py`(零新增依赖) |
| 4 | **设备放置错误** | transformers 在未传 `device_map` 时把模型放在 CPU(`if device_map is None: param_device = "cpu"`);原代码写成 `if dev != "cuda": model.to(dev)`,**有 GPU 时反而不搬运** → 14B 在 CPU 上做 15 次前向,单请求远超 90 秒上限 | 显式 `device_map={"":0}` 流式加载进显存,并保留 `model.to(dev)` 作为兜底 |
| 5 | **peft 惰性模块** | `peft 0.20.0` 会访问 `torch.distributed.tensor.DTensor`,未预加载则报 *module 'torch.distributed' has no attribute 'tensor'* | 在 `server.py` 最前面预加载该模块,并显式绑定到父包 |
| 6 | **docker-archive 元数据不一致(致命)** | `manifest.json` 的 `Config` 指向 `<hash>.json`,但包内实际文件名是 `config.json`。用 skopeo 复现旧镜像结果:`fatal: loading tar component c10d5c0e….json: file does not exist` —— **镜像根本无法被加载** | 两个文件名同时写入,`manifest` 指向标准哈希名;新镜像 skopeo 校验通过 |

该步骤专门确认"有 GPU 时模型必须真正搬到显卡上"这一关键点:早期版本写作
`if dev != "cuda": model.to(dev)`,而 transformers 在未传 `device_map` 时会把模型留在 CPU,
结果是**有 GPU 时反而不搬运**,14B 在 CPU 上跑 15 次前向,单请求远超 90 秒上限。

## 七、资源声明

| 资源 | 需求 |
|---|---|
| GPU | **≥ 48GB 显存**(两个基座模型 bf16 共约 42.5GB + 激活与 KV) |
| CPU | 8 核 |
| 内存 | 32GB(建议 64GB) |
| 磁盘 | 镜像约 50GB |
| 网络 | **不需要**(完全离线) |

**显存计算**:14B bf16 ≈ 28GB,7B bf16 ≈ 14.5GB,15 个 LoRA adapter 合计 < 1GB,
推理时 seq_len=512、batch=1,激活占用很小。

**不使用量化推理的原因**:`bitsandbytes==0.43.3` 依赖已被移除的 `triton.ops`(与 `triton 3.1.0` 冲突),
而 `0.45.0` 的 pip wheel 不含 GPU 支持。为保证**依赖可复现且行为与离线验证完全一致**,
最终采用 bf16 全精度推理,代价是显存需求提高到 48GB。

## 九、方案亮点

1. **完整的迭代自训练框架**:三轮伪标签迭代,每轮教师模型都在前一轮最优融合之上

5. **严格的数值稳定性处理**:识别并修复 softmax 饱和问题(`frac==max` 49.5% → 0.10%)
6. **交付级工程验证**:依赖闭包、ABI 一致性、设备放置、探针语义、镜像元数据逐项实测通过
