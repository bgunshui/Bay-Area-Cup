# 湾区杯 · AI 生成文本鉴别 · 技术方案报告

> 2026-10-02 依据仓库 `a5a7954` 的代码、冻结数组和提交 CSV 核对修订。
> 最终文本 AUC **0.981301** 已由交接方和答辩负责人确认；仓库没有官方成绩截图及复赛真标签，不能将本地一致性检查写成成绩复测。

## 一、项目解决什么问题

输入一段文本，输出用于区分 AI 生成文本与人类文本的分数，高分更倾向于 AI。AUC 评价正负样本的排序能力，`0.981301` 不等于“98.13% 的文本判断正确”。服务输出没有经过概率校准实验，宜称“检测分数”。

方案在公开 Qwen2.5-Instruct 基座上用 LoRA 训练分类器，结合多种检测分支生成软伪标签，再用无标签复赛文本做自训练。最终以14B为主，少量加入7B输出，没有从零训练语言模型。

| 组件 | 基座 | 适配器 |
|---|---|---|
| 主分支 | Qwen2.5-14B-Instruct | p4，五折共5个 |
| 辅助分支 | Qwen2.5-7B-Instruct | r3a和r3b，两组各五折，共10个 |
| 融合 | 两侧权重0.90 / 0.10 | 共15个adapter，复用两个基座 |

7B应称“两组五折”，不是“十折交叉验证”。来源：[p97提交生成脚本](../code/fusion/p97_p4_7b_sweep.py)、[服务v4](../code/docker_submit/server_dual_v4.py)。

## 二、训练和伪标签的实际做法

### 2.1 数据

仓库提供1000条官方样例的标签及折分数组，每类500条，每折200条；不提供样例原文、复赛原文或复赛真标签。

以[14B自训练p43](../code/training/p43_14b_p2.py)为例，每折使用800条官方训练样例和全量20000条复赛文本，剩余200条官方样例用于验证。复赛文本参与训练，这是**转导式自训练**：利用目标集合的无标签文本做适应。代码读取的是伪标签数组，不能仅凭仓库证明整个历史过程中“从未访问某数据”“已删除全部副本”等行为。

是否允许这一用法需依据对应阶段的正式规则，仓库的规则转述不能替代官方原文。

### 2.2 软标签和权重

[mk_pseudo_v2.py](../code/fusion/mk_pseudo_v2.py)等脚本实现：

```python
rank = rankdata(scores, method="average") / (N + 1.0)
soft = sigmoid(4 * (rank - 0.5))
conf = clip(4 * abs(soft - 0.5), 0, 1)
```

并列采用平均秩。软标签理论范围约为**0.1192～0.8808**，有限样本端点略向内收缩，旧“0.08～0.92”错误。`conf` 是远离中点程度的启发式权重，不是校准后的标签正确概率。官方硬标签权重2.0，伪标签权重为conf；提高硬标签影响并不保证伪标签不会传播错误。

有 `mk_pseudo_best.py`、`mk_pseudo_v2.py`、`p73_mk_pseudo_v3.py` 等不同代构造脚本，但最终各adapter的完整运行命令、输入哈希及逐代日志未全部提供，不能把“所有最终模型完整经历三轮”写成已核验事实。

### 2.3 参数和模型选择

下面是**p43代码默认值**，不是未留存的最终运行命令：

| 项目 | 实现或默认值 |
|---|---|
| 模型 | Qwen2.5-14B-Instruct，序列分类头score，2个输出 |
| LoRA | r=16，alpha=32，dropout=0.05，q/k/v/o_proj |
| 损失 | BCEWithLogitsLoss(logits[:,0], target)，逐样本乘权重后取批均值 |
| 优化器 | AdamW，lr=5e-5，weight_decay=0.01 |
| 调度 | 线性调度，warmup为总步数10% |
| 训练 | 2 epochs，max_length=512 **tokens**，batch=4 |
| 梯度检查点 | 默认开启，可用参数关闭 |
| 输入/输出标识 | 默认pseudo_best_v2、后缀_p3；生成p4需要实际参数覆盖 |
| 最佳epoch | 按官方验证折的AUC保存 |

不同历史脚本的长度、batch和标签版本不同，应查实际参数，见[复现指南](07_复现指南.md)。512 tokens不等于512个汉字；长文本会截断，缺长度统计，不能保证覆盖几乎所有文本。

**官方样例确实参与模型选择。** p43用验证AUC选epoch，[p4_fusion.py](../code/fusion/p4_fusion.py)用OOF AUC搜索融合权重。旧“样例不用于选型”与代码矛盾。小样例表现不能保证目标域表现，但“噪声固定±0.01”“只有榜单可靠”也缺统计证据；反复用同一OOF或榜单选方案不等于独立保留集评估。

p43在验证AUC<0.5时对保存的预测数组取负，但保存adapter时没有同步翻转分类头或记录方向。服务直接取logits[:,0]，若历史某折触发翻转，其部署方向仍需核实。当前不能判断最终各折是否触发此分支。

## 三、离线提交与服务是两条计算链

### 3.1 提交生成代码

定义 `r(x)=rankdata(x, method="average")/(N+1)`，p97实际读取：

```python
p4 = r(load("lora14b_p4_replay.npy"))
a  = r(load("lora7b_distill_r3a_replay.npy"))
b  = r(load("lora7b_distill_r3b_replay.npy"))
score_offline = r(0.90 * p4 + 0.10 * (a + b) / 2)
```

p43先对逐折预测分别排名、按折平均，再排名保存replay。“先排名再平均”与“先平均再排名”通常不同，不能把replay一概替换成rank(raw_mean)。

**目前缺7B两组的精确replay输入及逐折raw文件，现有材料不能逐位重建提交。**

### 3.2 服务v4代码

逐条切换14B的5个adapter，再切换7B的10个adapter，取logits[:,0]：

```python
p14 = sigmoid(mean(logits_14B_p4_5_adapters))
p7  = sigmoid(mean(logits_7B_r3a_r3b_10_adapters))
score_service = 0.90 * p14 + 0.10 * p7
```

7B服务是**先对10个logit平均，再做一次sigmoid**。`p100_fusion_modes.py`和`analyze_deviation2.py`用的是两组各做sigmoid再平均，不能直接当作v4的同公式验证。

离线在秩空间聚合，服务在logit空间聚合，二者不保证同排序。rank缩减尺度差异，但有并列时不是严格均匀分布，标准差不恒为0.2887；sigmoid也不自动提供校准概率。

逐条请求不能现场知道未知集合的完整排名；sigmoid是当前实现的选择，不能断言任何逐样本设计都无法使用参考分布，也不能预先排除服务实现缺陷。

### 3.3 冻结数据复核

按仓库数组给定行顺序与20000行CSV比较，独立标准库实现与NumPy/SciPy交叉检查一致。数组不含id且缺原文，行与文本的对应关系仍需交接方证明。

| 比较 | Spearman | 平均秩不同的行数 | 最大分数绝对差 |
|---|---:|---:|---:|
| 旧README的raw_mean近似链 vs CSV | 0.9999998013 | 9341 | 0.0093495325 |
| fusion_offline_submitted.npy vs CSV | 0.9999995877 | 18062 | 0.0019999000 |
| fusion_online_image.npy vs CSV | 0.9998697006 | 19369 | 0.1618774523 |

三组raw_mean按服务公式重算，与冻结online最大差约1.25e-9，显示该冻结数组与算术式高度一致；它不验证模型输出或Docker运行。

显式处理并列后，CSV与冻结online有严格反序**218292对**，一侧并列、另一侧有序**279对**；受影响合计**218571 / 199990000，约0.10929%**。这是给定数组的排序比较，不是错误率或AUC差。

旧“逐位重建、最大差1.1e-16”“AUC预期不变”“204591对、无条件上界0.0020”不再作为已核验结论。旧分析使用的offline数组并非提交CSV，且flips()强制拆开并列、树更新与查询下标不一致。AUC上界需说明真实正负样本数并考虑跨类排序及并列变化；目前没有复赛真标签。

## 四、怎样解释实验成绩

以下保留**团队历史记录**，不是受控逐项消融或本次独立复算的官方AUC。榜单脚本写入的成绩常数不能替代官方反馈凭证。

| 历史记录 | AUC | 相邻记录算术差 |
|---|---:|---:|
| 早期基线，提交来源待映射 | 0.9615 | — |
| 多分支融合候选 | 0.978284 | +0.016784 |
| 14B自训练候选 | 0.979964 | +0.001680 |
| 双14B seed集成 | 0.980896 | +0.000932 |
| p4单模型候选 | 0.981069 | +0.000173 |
| 最终p4+7B，已确认成绩 | **0.981301** | **+0.000232** |

早期“0.9615=纯14B监督微调”存在来源冲突：p21及p4_fusion注释将其关联到7B候选，缺提交映射不能确定身份。

p4_report.json保存**43个分支**的OOF AUC及相关矩阵，主方案public家族权重为0，并非所有候选都进入最终教师。“48分支”可能指历史候选池，目前不能写成最终有效教师数量。

双seed 0.980896低于p4单模型0.981069，不能说集成稳定优于每个种子。最终比p4高0.000232是小幅增益；没有显著性检验或完整控制变量对照，不能推出“异构永远更好”“相关更低必然更好”“多样性比标签质量更重要”。

logit排序可减少某些softmax饱和造成的信息损失；旧45%、49.5%→0.10%缺对应原始输出与完整日志，不作为本次验证数字。见[关键实验结果](../evidence/关键实验结果.md)。

## 五、交付与验证状态

v4有三类健康探针及POST /predict，增加请求校验、空文本EOS后备、预热和adapter切换期间的推理锁。CUDA可用时bf16加载，不能称float32全精度。

仓库Dockerfile仍复制历史单模型server.py，依赖清单也与最终修复记录不同。最终说明依赖[增量镜像重建脚本](../code/verify/rebuild_image.py)，直接执行当前Dockerfile不会自动构建出文档描述的v4双模型镜像。

交接方记录新tar为53317416960字节（约49.66 GiB），SHA-256为 `a163a653d2aa05b7bd51ec6016fbc5aed51379f7802fbfbb9a39c231dc691f68`。本次未收到新tar；本地旧tar为47775201280字节（约44.49 GiB），源码匹配server_dual_v2.py。新旧镜像结论必须分开。

团队GPU报告记载启动约70.1秒、五条短文本平均约0.68秒，其中一条空串。不能扩展为最长输入、并发、完整测试集或所有48GB显卡的保证。报告来自chroot/宿主机GPU环境，缺完整日志，也不是本次独立docker load/run。边界见[验证证据一览](05_验证证据一览.md)及[GPU报告](验证-真机GPU报告.md)。

静态审查仍发现：v4对NaN先min/max裁剪，可能把异常映射为接近1的分数；缺adapter会跳过，没有强制5+10数量检查；GPU迁移异常被捕获后缺最终设备断言；7B加载失败时readiness不会成功。这些是待修代码风险，**本次只修正文档，未改算法和服务代码**。
