> 本文先帮助接手者讲清楚文本项目，再准备基础问答。演讲时长、PPT 页数和评审权重目前没有官方通知原件可核对，以下结构可按安排调整。

## 第一部分：先讲清楚项目在做什么

**一句话：判断一段文本是否具有 AI 生成特征，输出连续检测分数，以 AUC 评价排序能力。**

可以直接这样介绍：

> 这个项目做 AI 生成文本检测。我们使用公开的 Qwen 模型，通过 LoRA 微调让它学习文本分类；再把已有检测方案对无标签目标域文本的预测转换为软伪标签，继续训练学生模型。最终方案结合 14B 的五折结果与 7B 的两组五折结果，权重为 9:1。团队记录的最终复赛文本 AUC 为 0.981301，这个数字已由交接方确认。AUC 是排序指标，不能说成准确率 98.13%。

### 先记住这几个数字

| 数字 | 可以怎么说 | 依据与边界 |
|---|---|---|
| **0.981301** | 最终复赛文本 AUC | 交接方确认、团队记录；仓库没有官方成绩原件，无法用无标签预测独立复算 |
| **1000 / 5 折** | 官方样例资产为 1000 条，每折 200 条 | 仓库的 labels/folds 数组；每折其余 800 条进入训练 |
| **20000** | 冻结提交文件有 20000 行 | CSV 中有 20000 个不同 id；自训练代码使用无标签目标域文本 |
| **14B + 7B / 15 个适配器** | 两个基座，14B 五个、7B 两组各五个 LoRA | v4 服务的默认完整配置；不是 15 个完整基座，也不是一次十折交叉验证 |
| **0.90 : 0.10** | 14B 和 7B 的融合权重 | 离线 p97 与 v4 服务均使用该权重，但后处理不同 |
| **512 token** | v4 推理默认截断上限 | 限制计算长度；不代表所有长文本的信息都被保留 |

证据入口：[自训练代码 p43](../code/training/p43_14b_p2.py)、[离线提交生成 p97](../code/fusion/p97_p4_7b_sweep.py)、[v4 推理服务](../code/docker_submit/server_dual_v4.py)、[冻结提交 CSV](../submission/submit_p4_90_7b2_10.csv)、[样例标签与分折数组](../evidence/离线预测/)。

## 第二部分：建议按这条顺序讲

### 1. 任务与困难

带标签样例较少，团队因此探索怎样利用无标签复赛文本训练检测器。历史报告还提出改写、润色和分布差异的问题，但仓库没有附原始文本及完整分析结果，不能把改写强度或长度分布作为已独立核验的统计结论。

### 2. 教师产生软伪标签，学生继续训练

教师就是已有检测方案；学生就是接受伪标签训练的模型。不是让教师生成原文，而是让它对现有文本打参考分数。

以 `mk_pseudo_v2.py` 与 `p43_14b_p2.py` 为例：

```python
rank = rankdata(score, method="average") / (N + 1)
soft = sigmoid(4 * (rank - 0.5))
conf = clip(4 * abs(soft - 0.5), 0, 1)
loss = mean(BCEWithLogitsLoss(logits[:, 0], target) * weight)
```

`rank` 在 0 与 1 之间，因此 `soft` 的理论边界约为 **0.1192～0.8808**，不是 0.08～0.92。官方真实标签的样本权重为 2.0；伪标签样本的权重为 `conf`，越接近 0.5 权重越低。这些设计旨在降低伪标签错误的影响，不能保证完全不被带偏。不同历史脚本的权重设置并不全相同，讲配置时须指明脚本。

[伪标签生成代码](../code/fusion/mk_pseudo_v2.py) · [训练损失与 checkpoint 选择](../code/training/p43_14b_p2.py)

### 3. 最终集成与两条计算链路

**离线提交**的 p97 脚本读取各模型的已保存 `replay` 分数，先做全局排名归一化，再按 9:1 融合，最后再排名归一化：

```python
p4 = rank01(saved_replay_14B_p4)
a = rank01(saved_replay_7B_r3a)
b = rank01(saved_replay_7B_r3b)
score_offline = rank01(0.90 * p4 + 0.10 * (a + b) / 2)
```

**HTTP 服务**的 v4 代码串行切换适配器，取第一维 logit 的平均，再做 sigmoid：

```python
score_http = 0.90 * sigmoid(mean(logits_14B_p4)) \
           + 0.10 * sigmoid(mean(logits_7B_r3a_r3b))
```

两条链路后处理不同，数值与排序均可能有差异。**0.981301 对应离线提交的团队成绩记录，不能直接当作 HTTP 服务重新评测的成绩。**

仓库现有聚合数组与 CSV 的核对也不是逐位一致：按照现有 14B rank 数组和两份 7B raw mean 数组重建，最大分数差约 0.00935；保存的 `fusion_offline_submitted.npy` 与 CSV 最大差约 0.00200。不能继续宣称“仓库现有材料已精确还原提交”。完整历史 replay 输入、逐折数组及 id 对齐信息仍需补齐。

[p97 离线代码](../code/fusion/p97_p4_7b_sweep.py) · [v4 HTTP 代码](../code/docker_submit/server_dual_v4.py) · [历史精确核对脚本及其输入要求](../code/fusion/final_check.py)

### 4. 结果、交付和局限

主成绩讲 0.981301 即可。0.981069 是团队记录的纯 14B p4 五折方案，最终 14B + 7B 方案比它高 **0.000232**。这是该批复赛数据上的小幅差异；没有复赛真标签，当前无法做配对显著性检验，也不能保证换一批数据仍有提升。

服务代码提供三个健康探针和 `POST /predict`。团队 GPU 报告记录启动约 70.1 秒、五条短测试输入平均约 0.68 秒；其中包括空串。该测试使用镜像目录下的依赖、模型和服务代码在宿主 Python 上启动，**不是实际 `docker run`，也没有附完整原始日志**。这些数字可以作为团队有限测试记录引用，不能当作所有文本、硬件或并发条件下的保证。

## 第三部分：Q&A 预案（30 条）

每个回答先说核心结论；具体数字不确定时，说明需要原负责人补记录，不补编理由。

### A. 技术基础

**Q1. 为什么选 Qwen，为什么是 14B + 7B？**

> 使用的是公开的 Qwen 基座。历史代码探索了不同大小与不同特征方案，最终提交采用 14B 为主、7B 为辅的组合。可以说明最终配置与成绩；目前不能声称做过严格控制的全尺寸对比，或证明 14B 在所有场景最优。

依据：[代码索引](../code/README.md)、[p97](../code/fusion/p97_p4_7b_sweep.py)。

**Q2. LoRA 是什么？r=16、α=32 怎么解释？**

> LoRA 通过训练少量适配参数调整公开基座。p43 设置 r=16、α=32、dropout=0.05，作用于 q/k/v/o 投影层。r 控制适配更新的秩，α 控制缩放。仓库没有附 r=16 与 r=32 的完整消融，不能说两者实测持平。

依据：[p43 的 LoraConfig](../code/training/p43_14b_p2.py)。

**Q3. 为什么用第一维 logit？**

> p43 的二元交叉熵直接训练 `logits[:,0]`，推理取同一维。不能随便替换成两维 softmax 的第二类分数，因为那是另一种计算。原始 logit 还能避免提前映射到接近 0 或 1 后丢失数值分辨率；具体饱和比例需对应原始预测记录。

依据：[p43 的损失与 predict](../code/training/p43_14b_p2.py)。

**Q4. 512 token 够吗？长文本怎么办？**

> v4 服务将输入截断到默认 512 token，以控制计算量。超长部分可能被丢弃，因此不能承诺完整覆盖长文本。多窗口属于已有探索方向，若要证明更好，需要长文本子集或窗口对比实验。

依据：[v4 的 MAX_LEN 与分词](../code/docker_submit/server_dual_v4.py)。

**Q5. 15 个适配器怎么运行？**

> 两个基座分别加载适配器，按顺序切换并前向：14B 五次，7B 两组各五次。然后取各侧 logit 平均。`/predict` 有互斥锁，避免不同请求同时改变同一模型的 adapter。

依据：[v4 的 _load_worker、_mean_logit 与 _INFER_LOCK](../code/docker_submit/server_dual_v4.py)。

**Q6. sigmoid 后的数值就是 AI 概率吗？**

> 它是映射到 0～1 的检测分数。代码没有概率校准或校准评估，所以不应解释为真实的“有 80% 概率是 AI”。sigmoid 也不必然消除不同模型的尺度差异。

依据：[v4 的 _sig 与 _predict_text](../code/docker_submit/server_dual_v4.py)。

### B. 训练与结果

**Q7. 没有复赛标签，怎么选模型？**

> 有两个层次：p43 在每折训练中根据官方样例验证 AUC 选择最佳 epoch；候选提交的取舍参考团队记录的复赛反馈。不能说官方样例绝不用于模型选择，也不能断言用小样例选型一定错误。频繁参考榜单仍有对榜单过拟合的风险。

依据：[p43 的 best_auc/best_state](../code/training/p43_14b_p2.py)、[权重候选生成 p97](../code/fusion/p97_p4_7b_sweep.py)。

**Q8. 用测试文本训练，是不是使用了测试答案？**

> 自训练代码用的是复赛文本及模型产生的软标签，没有读取复赛真标签。这属于利用目标域无标签信息的转导式学习。比赛是否允许，须以完整规则或组委会答复为准；仓库目前只有团队转述，不能仅凭代码宣布合规已获官方确认。

依据：[p43 的 train/test 与 target 来源](../code/training/p43_14b_p2.py)、[伪标签生成](../code/fusion/mk_pseudo_v2.py)。

**Q9. 怎么证明提升来自自训练？**

> 团队历史记录列出了监督基线、教师融合、自训练与最终集成的成绩。它们说明探索过程，但不是所有变量都受控的配对消融。要严格分离自训练贡献，需要同基座、同种子和同配置的有无伪标签对照，以及原始评测记录。

**Q10. 0.981069 与 0.981301 有什么区别？**

> 0.981069 是团队记录的纯 14B p4 五折方案，0.981301 是加入 10% 的 7B 两组五折结果后的最终离线提交。前者也已经包含五折集成，不能叫一个单折模型。

依据：[p87 纯 p4 候选](../code/fusion/p87_p4_only.py)、[p98 成绩记录](../code/fusion/p98_our_score.py)。

**Q11. 提升 0.000232 有统计意义吗？**

> 这是很小的榜单分数差。仓库没有复赛真标签和置信区间，当前不能判断统计显著性，也不能保证稳定提升。可以说在这一批复赛数据的记录中，最终组合分数更高。

**Q12. 多种子集成一定更好吗？**

> 不一定。团队记录中的双 14B 集成为 0.980896，低于纯 p4 的 0.981069；p5 的脚本还标注 0.979225。种子与集成都是探索手段，最终需要验证，不能把“平均后必优于最好单支”当作结论。

依据：[p91 成绩对照](../code/fusion/p91_scoreboard3.py)、[p92 p4/p5 对照](../code/fusion/p92_p4p5_local.py)。

### C. 泛化与工程环境

**Q13. 换一个生成模型，检测还准吗？**

> 当前可引用的成绩来自这批复赛数据。代码探索了公开检测器、似然和隐藏态等不同来源的信号，但没有完整的未见生成模型测试结果，不能保证跨模型效果。需要独立的跨来源测试集验证。

依据：[特征代码目录](../code/features/)。

**Q14. 随便换依赖版本能跑吗？**

> 不能默认兼容。v4 服务专门预加载 `torch.distributed.tensor`，构建修复脚本处理 Python ABI 的依赖覆盖。团队 GPU 报告记录了一套成功使用的版本，但它不是“其它版本都不能用”的证明。仓库原 Dockerfile 与 requirements 仍对应早期构建，不能拿来直接解释新版镜像。

依据：[v4 预加载](../code/docker_submit/server_dual_v4.py)、[依赖层构建脚本](../code/verify/build_deps_layer.py)、[团队 GPU 报告](验证-真机GPU报告.md)。

### D. 方法与一致性

**Q15. 创新在哪里？是不是从零自研大模型？**

> 基座与 LoRA 都采用公开技术。项目工作主要在小样本任务上的方案组合：多来源检测信号、软伪标签与置信加权、自训练，以及最终集成。可以讲针对赛题的设计与工程实现，不能声称从零训练基座或首创自训练算法。

**Q16. 线上和离线为什么不同？能完全复现吗？**

> p97 离线用整批数据的排名，v4 HTTP 服务逐条用平均 logit 后的 sigmoid，算法确实不同。整批 rank 不能直接由一条输入算出，但也不能说 sigmoid 是唯一可行方案。仓库现有数组尚不能逐位还原冻结 CSV；更不能把相关性高说成线上 AUC 已经一致。

依据：[p97](../code/fusion/p97_p4_7b_sweep.py)、[v4](../code/docker_submit/server_dual_v4.py)、[final_check 的历史输入](../code/fusion/final_check.py)。

> 若追问 AUC 偏差：没有真标签就无法直接复算差值。按排序变化给上界时，分母应是实际正负样本对数 `n_pos * n_neg`，不能无条件假设复赛正负各 10000；样例的 500/500 不证明复赛同样平衡。

### E. 效率与交付

**Q17. 为什么显存要求高？**

> v4 GPU 分支采用 bf16 加载两个基座和多组适配器，没有调用 8-bit 量化。团队报告记录显存约 41,868 MiB（约 40.9 GiB）。实际能否部署要看可用显存、运行环境和测试结果；bf16 不是 FP32，也不意味着线上离线计算一致。

依据：[v4 的 dtype 与加载](../code/docker_submit/server_dual_v4.py)、[团队 GPU 报告](验证-真机GPU报告.md)。

**Q18. 0.68 秒可以推算百万条耗时吗？**

> 不宜当作生产承诺。这个均值仅来自五条短测试输入，含空串；长输入、并发与排队会改变耗时。v4 的锁串行化了请求。批处理、多设备或减少分支是待评估优化方向，当前没有吞吐测试支撑。

依据：[gpu_driver 的 TEXTS 与计时](../code/verify/gpu_driver.py)、[v4 请求锁](../code/docker_submit/server_dual_v4.py)。

**Q19. 为什么镜像约 50 GB？**

> 团队交付说明称模型权重、适配器和依赖都放在镜像内，以离线方式运行，所以体积较大。Git 仓库本身不包含这些大权重；当前接手者也没有收到修复后镜像，不能用旧镜像代表新版交付物。

依据：[权重交接清单](../WEIGHTS.md)、[镜像信息](镜像信息.txt)。

**Q20. 怎么验证交付？**

> 仓库有归档、ABI、权重完整性、chroot HTTP 和 GPU 测试工具。工具存在与团队报告不等于本次已重跑通过。GPU 驱动采用宿主 Python 读取镜像目录，不是实际 Docker 运行；完整日志、真实容器启动和全量分数一致性仍应由负责人补证据。

依据：[验证工具目录](../code/verify/)、[gpu_driver](../code/verify/gpu_driver.py)。

### F. 应用价值

**Q21. 实际业务怎么用？**

> 接口可给文本返回连续检测分数，用于辅助排序和人工复核。业务阈值、误报率及校准需要在真实业务数据上确定，不能仅凭复赛 AUC 直接设定一个通用阈值。

**Q22. 会不会误判人类文本？**

> 会有这个可能。AUC 衡量整体排序，不给出某个阈值下的误报率。软伪标签是训练设计，也不保证最终分数保守。业务上应结合人工复核与其它证据。

**Q23. 落地还缺什么？**

> 需要代表业务的数据测试、误报与漏报分析、阈值或校准评估，以及长文本和并发性能验证。复赛成绩是一个数据集上的结果，不能自动覆盖这些要求。

### G. 进一步追问

**Q24. 伪标签会把错误放大吗？**

> 有风险。p43 用软标签、低置信权重和真实标签加权来减轻影响，但没有理论保证。几次候选分数上升也不能证明错误从未放大，需要独立对照和错误分析。

依据：[p43 的 conf、rows 与 loss](../code/training/p43_14b_p2.py)。

**Q25. 为什么不直接问大模型“是不是 AI 写的”？**

> 本项目采用可训练分类器与数值评分链路。代码中的 LLM 似然分支是在计算文本的语言模型特征，不等同于零样本问答。当前没有充分的零样本 prompt 对照，不能宣称这种方式必然差。

依据：[特征代码目录](../code/features/)。

**Q26. 训练用了多久、多少张卡？**

> 仓库脚本反映了多次训练探索，但缺完整启动命令、日志及算力账单。我可以讲已确认的方法与配置；总训练时长、卡数和成本由原训练负责人补充，不能用推理测试来估算。

**Q27. 只能讲一个关键设计，讲什么？**

> 讲软伪标签自训练：把已有方案的排序转为连续监督信号，低置信样本权重更低，同时保留真实标签监督。公式与代码能直接对应，最容易讲清。不要把特定增益称为已严格分离的最大创新贡献。

依据：[mk_pseudo_v2](../code/fusion/mk_pseudo_v2.py)、[p43](../code/training/p43_14b_p2.py)。

**Q28. 实验中有什么值得注意的发现？**

> 最好单一方案与集成方案的关系需要实测：双 14B 集成没有超过纯 p4，而最终加入少量 7B 后，团队记录分数略高。可以说模型组合并非越多越好，不能据一次结果推导“异构一定优于同构”。

依据：[p91](../code/fusion/p91_scoreboard3.py)、[p98](../code/fusion/p98_our_score.py)。

**Q29. 主要局限是什么？**

> 利用了目标域无标签文本，换分布需要重新验证；长输入被截断；双模型服务资源需求较高；离线 rank 与逐条 HTTP 后处理不一致；当前还缺概率校准、跨来源评测与完整复现证据。

**Q30. 后续怎么改进？**

> 可先补齐提交输入与日志、统一训练和服务预处理、评估能够逐条计算的后处理，再做业务测试与性能优化。这是建议方向，不代替团队未来承诺；迁移到图像、代码或语音也需要重新设计和验证。

## 第四部分：答辩表达注意事项

- 分清“代码采用”“团队记录”“尚未验证”，不要用一个层次替代另一个。
- 说 AUC 0.981301，不说准确率 98.13%；没有官方凭证时不强调名次。
- 说 14B 五折与 7B 两组五折，不说十折交叉验证；说 15 个适配器，不说 15 个独立大模型。
- 如实说明用过无标签复赛文本，也用样例验证 AUC 选 checkpoint。
- 说探索过多个候选分支，不说 48 个分支在最终教师或服务里同时非零运行。p2AD 的具体组合可查 [p77](../code/training/p77_reproduce_p2ad.py)，最终服务则是两个基座加适配器。
- 不把分数相关性、小幅榜单增益或五条短输入测试扩展为完全一致、稳定提升或生产性能保证。
- 对自己未参与且没有记录的训练细节，直接说由原负责人提供原始记录。接手答辩不需要假装亲自完成每次训练。

建议先准备一张流程图、一页最终配置，以及这份问答。暂不把现场加载镜像当作必需环节；新版镜像尚未交接，若以后安排演示，应先在演示机器上验证，再使用已有截图或录像作为备选。

## 第五部分：仍需负责人补充的材料

| 材料 | 用途 |
|---|---|
| 官方成绩截图、提交记录与答辩通知 | 核实成绩来源、名次、时长和评审权重 |
| 完整规则或组委会对无标签目标域自训练的回复 | 核实规则口径 |
| p97 使用的完整 replay 输入、逐折数组及 id 映射 | 解释现有数组与冻结 CSV 的差异 |
| 最终训练启动命令、adapter 配置/meta 与原始日志 | 核实实际超参数、种子、教师版本、耗时和资源 |
| 修复后镜像及其校验值、真实容器运行日志 | 核实交付版本与运行行为 |
| 配对消融、跨来源与长文本测试（如团队实际做过） | 支撑增益归因、泛化和性能结论 |

缺少这些材料不等于项目无效；它意味着相应结论暂时只能按证据边界回答。
