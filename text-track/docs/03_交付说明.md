## 二、历史镜像重建流程

历史记录的最终镜像采用两层归档：

```text
newlayer.tar   47,775,191,040 B  旧主层：系统、基座模型、15 个 adapter、旧服务
deps_layer.tar  5,542,215,680 B  cp310 依赖和额外覆盖文件，包括 v4 服务及 healthcheck
```

`code/verify/build_deps_layer.py` 解包外部 wheel 目录，写 whiteout，并从外部 `applayer` 复制覆盖文件；`rebuild_image.py` 追加依赖层、修改 manifest 与健康检查配置。脚本硬编码历史 Windows/WSL 路径，部分步骤删除 staging/输出文件，需审查配置并准备完整资产后使用。

当前 `code/docker_submit/Dockerfile`、`requirements.txt` 和 `docs/Dockerfile-构建用.txt` 保留的是单 14B、8-bit 历史方案，不能直接构建报告中的 v4 镜像。最终依赖 wheel 清单、额外覆盖目录及正确镜像未随本次 checkout 提供，重建流程不是现成的一键复现。

## 三、源码能确认的修复

| 问题 | 当前修法与证据 | 边界 |
|---|---|---|
| manifest 引用的配置文件不存在 | `rebuild_image.py` 同时写 `config.json` 与哈希名配置，manifest 指向后者 | 新镜像二进制仍待取得与核验；未 Docker 实跑 |
| 历史 CPython ABI / 依赖缺失 | `build_deps_layer.py` 追加 cp310 wheel、重定位文件并清理旧 torch 元数据 | 124 个 cp312 文件、57 个 wheel 等数量来自历史报告；目录本身未入库 |
| v2 有 GPU 时没有明确搬运 | v4 使用 `device_map={"":0}`，并尝试 `.to(dev)` | 兜底搬运失败后未强制检查设备；旧版本 CPU 延迟未在本次测量 |
| 共享模型切换 adapter 的竞态 | v4 对整次预测使用 `_INFER_LOCK` | 请求推理串行化；未测并发排队和吞吐 |
| 空输入导致零长度张量 | v4 在分词张量为空时补 EOS | 空文本的分数不代表有意义的分类判断 |
| distributed.tensor 属性可见性 | v4 预加载并显式绑定父模块属性 | 依赖兼容性仍需在实际部署环境确认 |
| 缺字段的 HTTP 422 与交付约定不同 | v4 的校验处理器返回 400/40001 | 非法请求 `req_id=None`，不是原样回传所有请求 |
| 首请求前尚未预热 | v4 预热后再设置 `ready=True` | 不检查预期适配器数量或输出是否有限 |
| curl 健康检查的依赖 | 重建脚本切换为 Python 标准库 `healthcheck.py` | 探测 liveness，不证明模型 ready；历史 Dockerfile 则安装 curl |

完整配置是 14B p4 五个 adapter 加 7B 两个版本各五个 adapter；14B 前向五次、7B 前向十次，共十五次，不是“14B 前向十五次”。

## 四、精度与资源口径

最终 v4 选择 CUDA bf16 / CPU fp32，未使用量化。“bf16”不应写成 FP32 全精度。历史材料记录 bitsandbytes / Triton 的兼容问题，但当前没有完整安装日志，不能泛化为某版本的所有 wheel 都不支持 GPU。

基座磁盘权重合计约 41.70 GiB；adapter 权重合计 907,824,320 B，约 865.77 MiB（约 908 MB）。模型文件大小与运行显存不可直接互换。历史报告的 41,868 MiB 显存占用换算为约 40.89 GiB；≥48 GB 显存是历史交付建议，未在当前环境重新测定。

不能直接建议“去掉 7B 就能在 24 GB 上运行”：14B 未量化基座本身的文件体积约 27.51 GiB。改用量化、单模型或其他设备配置会改变部署与可能的分数，需重新验证。

## 五、已有验证材料分别证明什么

| 材料 | 覆盖 | 不覆盖 |
|---|---|---|
| 归档/权重审计脚本 | 配置引用、层哈希、有效文件比较、safetensors 头/区间/文件大小、分片名称 | 不是模型精度验证；部分脚本只打印结果，不能只看退出码 |

| `gpu_driver.py` 及历史 GPU 报告 | 宿主 Python 挂镜像依赖，v4 真模型的五条短样本顺序烟测 | 未 Docker 实跑、未并发/最长输入测试、未复赛全量 AUC；完整日志未入库 |

历史归档解析与 GPU 指标见相应报告，属于留存记录。本次可直接核实代码和已经交接的旧镜像静态内容；未重新执行上述历史验证。

## 六、当前仍需披露的风险

1. v4 的 NaN 检查在分数夹取后，sigmoid 内也先夹取；异常数值可能被变成边界分数，保护不可靠。
2. adapter 不存在时静默跳过，未验证 5＋5＋5 完整数量。
3. `.to(dev)` 失败仅打印，未断言模型确实在目标设备；推理异常也没有堆栈日志。
4. GPU 烟测仅五条短文本，完整服务日志和设备原始输出未入库；0.68 s 不能推广至任意输入与并发。
5. 没有真实 `docker load` / `docker run` 证据；正确最终镜像未在当前交接目录提供。
6. 线上是 logit 平均后 sigmoid 融合，官方 CSV 是每折全局 rank 后平均再融合，二者不完全一致。详见 [04_镜像复现偏差说明-回组委会.md](04_镜像复现偏差说明-回组委会.md)。

这些限制不否定已经实现的工程修复，但应在交接与答辩中明确保留。
