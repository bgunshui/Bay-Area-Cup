## 二、镜像分层设计

镜像**不是** `docker build` 出来的,而是手工拼装的两层归档:

```
newlayer.tar    (47,775,191,040 B)  基座 = python:3.10-slim
                                    + 两个基座模型(41.7 GiB)
                                    + /app/{server.py, adapters/}
deps_layer.tar  ( 5,542,215,680 B)  完整 Python 依赖闭包(57 个 cp310 wheel)
                                    + 覆盖版 /app/server.py(v4)
                                    + /usr/local/bin/healthcheck.py
```

**为什么这么设计**:主层有 44 GB 的模型权重,任何一次依赖修正都重新生成主层是不可接受的
(单次组装要十几分钟且占用 90 GB 磁盘)。改成"追加一个依赖层"后,
依赖问题可以在 5 GB 的层里独立迭代。

## 三、修掉的 6 个问题(其中 2 个是致命的)

### 🔴 致命 1:归档元数据不一致 —— 镜像根本 load 不进去

`manifest.json` 的 `Config` 指向 `<hash>.json`,但包内实际文件名是 `config.json`。

用第三方解析器复现,旧镜像直接失败:

```
$ skopeo inspect docker-archive:旧镜像.tar
fatal: loading tar component c10d5c0e….json: file does not exist
```

**修法**:两个文件名同时写入,`manifest` 指向标准哈希名(`<sha256>.json`)。

### 🔴 致命 2:CPython ABI 错配 —— `import torch` 直接失败

主层里 torch / scipy / tokenizers / sentencepiece / functorch 共 **124 个 `.so`
是 cpython-312 的编译产物**,而镜像是 Python 3.10。

```
ImportError: Failed to load PyTorch C extensions:
  It appears that PyTorch has loaded the `torch/_C` folder …
```

更进一步:即使侥幸加载,`libtorch_python.so` 也会因
`undefined symbol: PyObject_CallOneArg`(3.12 导出、3.10 不导出)而失败。

**修法**:依赖层全部替换为 **cp310** 版本,并用 whiteout 清掉旧 `torch-*.dist-info`。

### 🟠 3:依赖闭包不完整(119 个传递依赖缺失)

最初构建用了 `pip download --no-deps`,只解包了 10 个直接依赖,
numpy / sympy / networkx / fsspec / jinja2 / `nvidia-*`(12 件)/ triton 等 **119 个全缺**。

**修法**:在 **Linux** 环境解析完整闭包 —— 这一步有个坑:
pip 的 `--platform` **不评估** `platform_system == "Linux"` 标记,
在 Windows 上解析会把 `nvidia-*` / `triton` 全部跳过。

### 🟠 4:设备放置错误 —— 有 GPU 时模型反而不搬到显卡

```python
dev = "cuda" if torch.cuda.is_available() else "cpu"
...
if dev != "cuda":          # ← 有 GPU 时这个分支不进,模型留在 CPU!
    model = model.to(dev)
```

transformers 在**未传 `device_map`** 时把模型放在 CPU
(`modeling_utils.py`: `if device_map is None: param_device = "cpu"`)。
后果:14B 在 CPU 上跑 15 次前向,**单请求远超 90 秒上限**,决赛必然失败。

**修法**:显式 `device_map={"": 0}` 流式加载进显存,并保留 `model.to(dev)` 兜底。
真机日志确认:

```
[load] …/Qwen2.5-14B-Instruct 经 device_map 加载到 cuda:0
[load] lora14b_p4 基座就位 device=cuda:0 dtype=torch.bfloat16
```

### 🟠 5:`curl` 缺失但 HEALTHCHECK 依赖它

`python:3.10-slim` 里没有 curl,而原 HEALTHCHECK 是 `curl -f … || exit 1`
→ 容器**恒为 unhealthy**。

**修法**:改为等价的 Python 标准库实现 `healthcheck.py`(零新增依赖),
并把配置里的 `Healthcheck.Test` 改成 `["CMD","python","/usr/local/bin/healthcheck.py"]`。

### 🟡 6:`peft 0.20.0` 需要预加载惰性模块

peft 会访问 `torch.distributed.tensor.DTensor`,而它是惰性子模块:

```
AttributeError: module 'torch.distributed' has no attribute 'tensor'
```

**修法**:在 import peft 之前先 `import torch.distributed.tensor`,
并在预加载后**显式绑定**到父包(双保险)。

## 四、为什么不用 8-bit 量化(显存从 18 GB 涨到 48 GB)

| 方案 | 问题 |
|---|---|
| `bitsandbytes 0.43.3` | 依赖已被移除的 `triton.ops`,与 `triton 3.1.0` 冲突 |
| `bitsandbytes 0.45.0` | pip wheel **不含 GPU 支持** |

为保证**依赖可复现、且线上行为与离线验证一致**,最终采用 **bf16 全精度**,
代价是显存需求升到 48 GB。这是一个明确取舍,答辩时应主动讲。

> 如果平台只提供 24 GB 卡,降级路径:① 只跑 14B(去掉 7B 分支);
> ② 合并 LoRA 到基座后引入量化的 7B 分支。

## 五、验证层级(逐级加严)

| 层级 | 手段 | 结果 |
|---|---|---|
| 1 | 依赖自检:41 个发行版 + 23 个模块 import | 全通过 |
| 2 | 分层 sha256 vs `config.rootfs.diff_ids` | 逐字节一致 |
| 3 | 第三方解析器 skopeo 校验归档格式 | 通过 |
| 4 | 权重完整性:27 个 safetensors / 5,093 个 tensor | 异常 0 |
| 5 | chroot 内以镜像原样 `CMD` 起服务 + **真实 HTTP** | 三探针 + `/predict` 全通过 |
| 6 | 真机 RTX 4090 加载真实权重 + 15 个适配器 | 70.1 s 启动 / 0.68 s 单条 |

**为什么要做第 3、4 层**:第 2 层是"用自家脚本自证",不够。
第 3 层换第三方实现(skopeo / containers-image,与 podman 同源)独立解析;
第 4 层则补上了"解析得出来"与"权重真的完整"之间的空档 ——
safetensors 的头部解析 + 字节区间连续性 + 大小自洽,能查出截断/损坏。

## 六、已知偏离与局限(主动披露)

1. **镜像内没有 curl**:见上文第 5 条。若评测方自身要在容器内 `docker exec … curl` 探测,
   需要额外补静态 curl —— 按标准文档的流程(平台从外部 HTTP 探测)判断不需要。
2. **主层仍残留 124 个 cp312 的 `.so`**:已被依赖层 cp310 覆盖全部同名路径,
   Python 3.10 只加载 cp310 后缀,残留不参与导入。约 115 MB 死重,无功能影响。
3. **`repositories` 里记的是 layer chainID**:现代 Docker(25+/29)已移除 v0/v1 旧加载路径,
   该文件不再被读取,tag 由 `manifest.json` 的 `RepoTags` 决定。
4. **未做真实 `docker load` + `docker run`** 全流程:开发环境与可用服务器均无 Docker 守护进程。
   替代验证是第 3–6 层。
5. **容器以 root 运行**、**镜像体积 50 GB**(赛题无体积上限)。
