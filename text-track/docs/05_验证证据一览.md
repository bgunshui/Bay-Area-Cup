## 二、归档与依赖验证覆盖

`audit_A_archive.py` 对历史 `D:\文本附件资料.tar` 检查成员、报告字节比较及镜像哈希；`audit_BCD_image.py` 对有效 server/healthcheck、safetensors 头/连续区间/文件大小及分片名称做检查。`wsl_verify_image.py` 才检查各层哈希与 diff_ids，并抽取环境、应用 whiteout；`check_archive.py` 仅列包成员、计算包内镜像哈希并打印 MATCH/MISMATCH。

这些脚本保留历史绝对路径，不能把文中的命令当成当前 checkout 可直接运行的通用命令。抽取与构建脚本还会删除目标目录、覆盖输出，需要准备正确资产并审查路径。当前未重新运行。

脚本也有明确盲区：`audit_BCD_image.py` 的 requirements 缺失分支不会自动加入问题清单；头 JSON 解析失败仅增加 `bad` 计数，部分失败可能不影响最终退出码；它没有校验每个 tensor 的 dtype/shape 与数据区字节数一致，也没有验证权重内容的模型含义。因此“退出 0”不能概括为所有内容均无缺陷。

历史终审报告中的“Config 存在、v4 有效、依赖 import 通过”等是历史记录。当前可见 v4 源码哈希与该记录一致，最终二进制及其完整验证输出待交接。

## 三、chroot 验证分别做了什么

| 阶段 / 脚本 | 代码实际做法 | 可以证明的范围 |
|---|---|---|
| `chroot_test.py` | `from_config` 初始化一层、词表 1000 的模型，挂部分真实 adapter，随机 token 前向 | 依赖与缩小模型/adapter 的加载兼容路径 |
| `chroot_e2e.py` | 一层、词表 2000 的模型，token id 取模，默认每组 2 折；直接调用 Python 接口函数 | 缩小模型上的融合函数与响应构造；不是 HTTP 全量模型服务 |
| `chroot_http_driver.py` 阶段 1 | 原 `python server.py`，模型目录故意不存在 | 服务可监听及加载失败时探针语义 |
| 同脚本阶段 2 | 启 `chroot_fake_server.py`，替换 `_load_worker`；一层、词表 1500、token id 取模、默认每组 2 折 | 真实 HTTP 的烟测、部分 adapter 切换和 400/40001；不是完整基座加载 |

以上历史报告中的分数仅供链路检查，无检测质量或 AUC 含义。不能将两个阶段合并说成“镜像原样 CMD 加载完整模型端到端通过”。

## 四、真机 GPU 记录的强度与缺口

历史报告称在 Ubuntu 22.04 / Python 3.10.12 宿主，以 `PYTHONPATH` 使用抽取的镜像依赖并运行 v4；镜像自身 Python 记录为 3.10.21。它避免了完整 Docker 隔离，因此不能代替 Docker 的加载、GPU 注入、网络及健康检查全流程。

`code/verify/gpu_driver.py` 的 `TEXTS` 只有中文评论、论文风格短文、短句、英文、空串共五条，逐条请求、每条一次。源码最多截断 512 tokens，不代表这次测试实际覆盖该长度。驱动启动的服务器文件是 `/root/sj-tmp/server_v4.py`，未校验运行文件的 SHA256；`/root/sj-tmp/gpu_server.log` 与完整驱动 stdout 未入库。

[`验证-真机GPU报告.md`](验证-真机GPU报告.md) 保留耗时和设备日志摘录，可作为历史烟测记录。尚不能据此宣称独立完整运行日志已齐、所有输入小于 90 秒、高并发可靠、Docker 可直接部署或镜像全量 AUC 为 0.981301。

## 五、线上 / 离线融合差异

历史离线公式记录：每折 `rank01(logit)` 后平均，14B 与两组 7B 融合后再 `rank01`；但当前合并数组/简式不能逐位复现CSV。线上：14B 五折原始 logit 平均后 sigmoid，7B 十个原始 logit 平均后 sigmoid，最后 0.90/0.10 加权。折间聚合空间与跨模型分数尺度都不同。

逐条 HTTP 不直接拥有全测试集全局排名；当前实现采用 sigmoid 替代。不能说这是唯一可能的部署方法，也不能说两条链路完全等价。说明文档见 [04_镜像复现偏差说明-回组委会.md](04_镜像复现偏差说明-回组委会.md)。该文件名链接按实际路径修正；是否已经发送回复需另有邮件记录，文档标题不能证明发送状态。
