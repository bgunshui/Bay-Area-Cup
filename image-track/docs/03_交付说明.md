## 二、怎么用

### 1. 跑镜像（推荐路径）

```bash
docker load -i Docker镜像/baycup_image_aidet_0.918887.tar
docker run --gpus all -p 8080:8080 baycup-image-aidet:0.918887
```

启动后（**约 60–120 秒**）提供规范要求的三个探针与统一推理端点：

| 接口 | 用途 |
|---|---|
| `GET /health/startup` | 模型全部加载完才 200；加载期 503，平台会重试 |
| `GET /health/liveness` | 只反映进程存活（< 1 ms，不碰模型） |
| `GET /health/readiness` | 200 即保证紧接着的 `/predict` 可用 |
| `POST /predict` | `{"req_id","data"(base64 图像)}` → `{"req_id","code":0,"score"}` |

**资源需求**：GPU 显存 **≥ 10 GB**（实测峰值 ~9 GB）、4 核 CPU、**≥ 8 GB 内存**（建议 16 GB）。
**单张推理 0.2–0.5 秒**（标准上限 90 秒）。**运行期不联网**。

### 2. 不想跑镜像，只想复核成绩

```bash
python 构建与复现套件/docker_submit/verify_reproduce.py --from-csv
# 必须输出 spearman = 1.0000000000
```

这条**不需要 GPU、不需要 Docker、不需要模型权重**，只用包里的 10 个冻结 CSV 就能
**逐图重建** 0.918887 的提交文件（20000 行）。

### 3. 想自己构建 / 复检镜像

```bash
cd 构建与复现套件/docker_submit
bash build.sh                          # 有 Docker：下载骨干 → build → 冒烟 → save
bash verify_container.sh <镜像.tar>     # 没有 Docker / 没有 GPU：用 chroot 做成品复检
```

## 三、这一版镜像修了两个真实缺陷

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | **「镜像权重崩溃」**（上一版被驳回的原因） | 3 个骨干 `.safetensors` 的权限是 `-rw------- root:root`（fp16 转换脚本 umask=077；同目录的 `.bin` 是 `cp` 来的所以是 0644 —— **只有 safetensors 中招**），而容器 `User=appuser` ⇒ 加载骨干时 `PermissionError` | 构建时 `chmod -R a+rX`，并加**构建闸门**：以 appuser 逐个 `open()` 层内每个文件，有一个读不到就整体失败、不出镜像 |
| 2 | `HEALTHCHECK` 永远 `unhealthy` | pytorch 官方基座**不含 `curl` 可执行文件**（只有 `curl-config`），而 HEALTHCHECK 正是 `curl -f …` | 增补一层 2.5 MB 的 curl 层（curl 7.81.0 + 10 个缺失动态库；与基座同为 Ubuntu 22.04 jammy，ABI 一致，已实测 `ldd not found` = 0） |

两次修复都做了**独立复检**（不依赖 Docker、不依赖 GPU），逐项命令与实测输出见
`MANIFEST.md` 第二节、`docker_submit/verify_container.sh`，以及技术方案报告 §9。

## 四、交付前做过的验证（这是这份材料最该被看的部分）

我们用**镜像里的同一份代码 + 同一份权重 + 同一份查表**，在 **torch 2.5.1+cu124**（与镜像完全一致）
上对**官方测试集的真实图片**逐张推理，与冻结 CSV / 提交文件比对 spearman：

| 项目 | 1000 张实测 |
|---|---|
| `img_cliph_rerun`（占基底 42.25%） | **0.997625** |
| `img_cliph_s20261101 / 02 / 03` | **0.999772 / 0.999781 / 0.999781** |
| `img_gpp_siglip2` | **0.999910** |
| `img_bigg_rerun2 / rerun3` | **0.998456 / 0.999550** |
| `img_bigg_s384_retrain`（权重 **10.71%**） | 0.972605 |
| **最终融合 vs 提交文件** | **spearman = 0.999508** ✅ |

**关于 `img_bigg_s384_retrain` 这一格（如实说明，并给出它对最终分数的影响）**：
它**确实被用到**，最终权重 `0.107143`（槽 0.75/0.214/0.107 中的第三槽）。
我们在**最终分数空间里**做了精确消融（用交付包自身的 ECDF 查表反解）：

| 变体 | spearman vs 提交文件 |
|---|---|
| 现状（镜像算的 8 个分量） | **0.999508** |
| 只把这一格换成冻结 CSV（即"若它完美"） | 0.999891 |
| **⇒ 这一格带来的差距** | **+0.000382** |

即：**它的偏差只让融合排序一致度从 0.9999 降到 0.9995，对最终 AUC 的影响可以忽略。**
原因见报告 §9.7：我们打包的 LoRA 与产出该冻结 CSV 的 `best.pt` 是**同配方下的两次不同训练**
（已排除预处理、权重错配、精度三种可能 —— fp32+bf16 与 fp16 结果都是 0.9655），
而原始 run 目录位于已释放的实例盘、**无法再取回**。

**交付前一共抓出 9 个只有真跑（或真查）才会暴露的 bug，其中四个是致命的**：

> **① 同家族分量共用一份 LoRA**：`models.py` 把 8 个分量的 LoRA 加载进**共享的** peft 对象，
> 导致同家族分量**全部在用"最后加载的那个 LoRA"** —— 8 个里错 4 个，
> 包括**占基底权重 65% 的 `img_cliph_rerun`**（spearman 只有 0.335，正确是 0.999）。

> **② 骨干文件权限 `-rw------- root:root`**（本次被驳回的直接原因）：容器以 `appuser` 运行，
> 三个骨干一个都读不到 ⇒ 服务崩在加载骨干这一步。已在构建流程里加**逐文件 `open()` 闸门**。

> **③ `server.py` 预热用了短键名**：写成 `_M.score("cliph_rerun", …)`，而 `models.py` 的键
> 已统一成 CSV basename（`img_cliph_rerun`）⇒ 预热直接 `KeyError` ⇒ **启动/就绪探针永远 503**。
> 这是真跑一次 HTTP 才抓到的。

> **④ 镜像里没有 `curl`**：HEALTHCHECK 声明的 `curl -f …` 根本不存在 ⇒ 容器永远 `unhealthy`。
> 已补一个 2.5 MB 的 curl 层。

其余 5 个（`typing_extensions` 被误剪、`--no-deps` 漏装 `timm/httpx/typing-inspection/typer/cloudpickle`、
`pydantic-core` 版本冲突、`starlette` 违反 `<0.42.0`、`ocr` 路径残留）见技术方案报告 §9.3 的完整表格。
