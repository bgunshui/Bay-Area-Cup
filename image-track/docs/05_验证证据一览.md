## 四、偏差归因（消融与单变量实验）

### 4.1 翻转样本对分析（200 张，19,900 个样本对）

| 数值 | 含义 |
|---|---|
| **175 / 19,900 = 0.8794%** | 排序发生翻转的样本对占比 |
| 0.0050 / 0.0068 / 0.0647 | 秩位移 中位数 / 均值 / 最大 |
| 34 / 200（17.0%） | 秩位移 > 0.01 的样本数 |
| 2 / 200（1.0%） | 秩位移 > 0.05 的样本数 |
| **0.0066** | **翻转对**的冻结分 \|Δ\| 中位数 |
| **0.2933** | **全部样本对**的冻结分 \|Δ\| 中位数 |
| \|ΔAUC\| ≤ **0.0176** | 严格上界（最坏情形：全部翻转对恰好分属正负样本） |
| ≈ **1.3 × 10⁻⁵** | 翻转方向随机时的典型量级 |

> **关键判读**：翻转对的分数间距比全体小 **44 倍** ⇒ 翻转几乎只发生在"近乎并列"的样本对上，对 AUC 的实际贡献极小。

### 4.2 批大小是不是原因？——**单变量实测：不是**

固定同一份权重、同一预处理，**只改批大小**（对象 = 偏差最大的 `img_bigg_s384_retrain`）：

| 批大小 | spearman | 平均绝对差 | 最大绝对差 |
|---|---|---|---|
| 1（镜像实际） | 0.978482 | 0.0672 | **0.9977** |
| 4 | 0.978501 | 0.0673 | 0.9977 |
| 8（离线产出 CSV 时） | 0.978451 | 0.0672 | 0.9977 |
| 32 | 0.978451 | 0.0672 | 0.9977 |

> 四档**完全一致**（差异在 1e-5 量级）⇒ **批大小不是偏差来源**。
> 证据：`evidence/决定性实验_批大小单变量_BS1.log`、`..._BS4-32.log`
> ⚠️ 这个实验同时给出**决定性判据**：最大绝对差 **0.9977** 意味着存在一边判 ~1.0、另一边判 ~0.0 的样本 —— **远超 fp16/bf16 数值抖动的量级（约 1e-2）**，说明该分量的**权重本身不同**（同一配方下的两次不同训练），而非数值路径不同。

### 4.3 精度路径

| 数值 | 含义 |
|---|---|
| **0.9656** vs **0.9654** | 用**完全复刻训练侧的配置**（fp32 权重 + `autocast(bfloat16)`）重跑 vs 服务侧 fp16 —— 两者一致 ⇒ **精度不是该分量偏差的原因** |

### 4.4 单个分量的影响（精确消融）

用交付包自身的 ECDF 查表把融合分反解，**只替换这一格**：

| 变体 | 融合排序一致度 |
|---|---|
| 现状（镜像实际算出的 8 个分量） | 0.999508 |
| 仅把该分量替换为冻结值 | 0.999891 |
| **⇒ 该分量带来的差距** | **+0.000382** |

## 七、关键实验结论（支撑"技术深度"分）

### 7.1 数据量 vs 监督方式（同骨干同预处理的单变量对照）

| 模型 | 数据 | 与主分量 `cliph_rerun` 的相关 |
|---|---|---|
| `cliph300k` | CLIP-H + **302k 纯监督** | 0.7785 |
| `cliph_f2` | CLIP-H + **31k（1/10 数据）纯监督** | **0.8012** |
| `cliph_e2` | CLIP-H + 20000 **软标签** + Tiny 31369 硬标签 | **0.9315** |

> **结论：独立性来自"纯监督"这个方式，而不是数据规模**；一旦掺入教师软标签，独立性立刻退化。

### 7.2 "大模型/大数据更好"是错的（决定性对照）

| 模型 | 数据 | 骨干/预处理 | 探针 val_auc |
|---|---|---|---|
| `s384r`（在赢的基底里） | **Tiny 28.8k** | bigG@384 拉伸 R32 | **0.990400** |
| `s384_str300k` 的 25% checkpoint | **302k** | bigG@384 拉伸 R32（**同骨干同预处理同 rank**） | **0.723350** |

> 差 26.7 个点，唯一变量是数据集。

### 7.3 分量相关矩阵（决定"往哪里注入"）

| | cliph_rerun | cliph300k | gpp | cliph_f2 |
|---|---|---|---|---|
| cliph_rerun | 1.0000 | 0.7785 | 0.7914 | 0.8012 |
| cliph300k | 0.7785 | 1.0000 | **0.7403** | 0.8414 |
| gpp | 0.7914 | 0.7403 | 1.0000 | **0.6964** |

> `gpp`（LB 实测 **0.9054**）与 `cliph300k` 彼此只有 0.7403 相关 ⇒ **多源注入优于单源**。

### 7.4 尺寸先验

| 数值 | 含义 |
|---|---|
| **OOF AUC = 0.8247** | 尺寸先验单独强度（严格 5-fold CV） |
| **0.146** | 与模型的图片级相关（低相关 ⇒ 融合增益大） |
| 92.2% / 83.0% / 6.9% | 512×512 / 1024×1024 / 1024×683 的假图率 |
| 72.9% | 测试集中落在"可靠尺寸档（样例量≥11）"的比例 |

## 八、怎么自己复跑

> 下面所有命令的**当前目录都是 `image-track/`**（即本仓库里的赛道目录）。
> 每条都实际跑过；凡是需要特定环境的都已标注。

```bash
cd image-track           # ← 起点

# ① 最轻：只要 10 个 CSV，验"提交文件逐图可重建"（不需要 GPU / 权重 / Docker）
cd code/docker_submit
python -m venv .venv && .venv/bin/pip install -r requirements-verify.txt   # 约 1 分钟
.venv/bin/python verify_reproduce.py --from-csv
#    → 实测输出：spearman = 1.0000000000，max|Δ| = 7.500e-05
#    ⚠️ 需要 numpy ≥ 2（gbm.pkl 由 numpy 2.x 序列化）；版本不对脚本会提前拦住并给解法
cd ../..

# ② 校验提交文件格式合规（列名/20000 行/id 集合与顺序/范围/唯一值，并打印 md5）
python code/fusion/check_submission.py submission/v100_gpp20_seed4_c75_prior200.csv
#    → 通过  行=20000  范围=[0.000050, 0.999950]  唯一值=19981
#      md5 = 9cade3174f33da089883927113d6ce8f   ← 与 submission/README.md 的哈希台账一致
#    退出码 0=通过 / 1=有失败项（可脚本化调用）

# ③ 有 GPU 时：起服务并打三探针 + /predict（脚本是 bash，**需 Linux**）
bash code/docker_submit/verify_container.sh <镜像 tar>     # 用 chroot 摊开镜像，无需 Docker 守护进程
```
