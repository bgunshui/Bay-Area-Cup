## 0. 摘要（一页看完）

### 0.1 模型架构

**一个 8 模型后融合系统，单张图前向 → 一个 `score ∈ [0,1]`。**

```
一张图 ──▶ 8 个「冻结骨干 + LoRA + 线性头」
                ├─ CLIP ViT-H-14        ×4   （转导蒸馏学生）
                ├─ CLIP ViT-bigG-14     ×3   （224 / 384 两种分辨率）
                └─ SigLIP2-so400m-384   ×1   （纯监督独立模型）
             │
             ▼  8 个原始分
        ECDF(把每个分量的原始分映射成它在测试集分布上的百分位)
             │
             ▼  分槽 rank 加权
        主分量槽 0.75 · bigG 槽 0.214 · s384 槽 0.161
             │
             ▼  再叠一路「尺寸先验」（权重 0.20）
        GBDT(宽高/像素数/字节数/bpp/is_sq…) + 尺寸档查表 → ECDF
             │
             ▼
        ECDF → 最终 score
```

- **骨干全部冻结**，只训 **LoRA**（r=16/32，`lora_alpha=2r`）+ **一个线性头**；
  单模型 LoRA 参数量 0.3M–15.7M，8 个合计约 60 MB 量级。
- **融合全程走 rank / ECDF**，不是分数加权 —— 这样各分量量纲无需对齐，且对单调形变鲁棒。
- 最终权重：`0.42 cliph_rerun + 0.098 cliph300k + 0.13 gpp + 0.20×2 bigG + 0.107 s384 + 0.20 prior`。

### 0.2 训练策略

| 分量类别 | 数量 | 训练数据 | 监督方式 |
|---|---|---|---|
| **测试集转导蒸馏学生** | 4 | 测试集 20000 张（教师=上一版融合分数，**软标签**）+ 官方 sample 800 张硬标签 | 蒸馏 |
| **纯监督独立模型** | 3 | Tiny-GenImage 28.8k / GenImage++ 78k / 302k 真标签集 | 纯监督 |
| **尺寸先验** | 1 | 官方 sample 1000 的标注 | GBDT + 分档查表 |

- 统一配方：AdamW，LoRA 只训 A/B 与头，`bf16` autocast，1–2 epoch；
  **训练与推理使用同一套预处理**（`Resize((S,S), BICUBIC)` + CLIP 归一化，`interpolate_pos_encoding=True`）。
- **两条被实验证否的路线**（写在这里免得重走）：
  ① 「用自己数据微调」有害（sample val +4.5 点，LB 反跌 0.0035）；
  ② 「减主分量、加新分量」屡试屡负 —— 最优配比在**主分量更高处**。

### 0.3 关键实验结果（全部为 LB 实测）

|---|---|---|

## 2. 核心方法论：为什么是这套结构

### 2.1 出发点：什么才是有效的信号？

复赛测试集与初赛**不重叠**、**含对抗性样本、难度更高**。我们系统性穷举了各类信号并逐一用实验否证：

| 信号方向 | 实测结果 | 结论 |
|---|---|---|
| EXIF / ICC / 子采样等元数据 | 被赛事方**完全清除**（1000 张全空） | ❌ 不可用 |
| JPEG 量化表指纹 | 5-fold OOF AUC **0.4850** | ❌ 统一重压后已抹平 |
| 频谱 / 噪声等低层痕迹（166 维 FFT/DCT/SPAM 特征） | OOF AUC **0.7219**（LR）/ 0.7110（GBM） | ❌ 远低于深度模型 |
| 现成开源 AI 图像检测器（5 个 HF 模型） | 同批样例上最优 **0.7863**；我们自训模型同批 0.976~0.990 | ❌ 差距过大 |
| 测试集 id 轴的分块结构 | 所有 lag 自相关在 ±0.01414 内，与打乱对照同量级 | ❌ 无结构 |
| 用更大数据集训练（30 万张） | 同骨干同预处理下，val AUC 从 0.9904 掉到 0.7233 | ❌ **有害** |
| 换更大骨干（DINOv3-7B） | 与主分量 ρ=0.9223 且拟合更差 | ❌ 骨干不是瓶颈 |

**唯一有效且可复现的信号来源，是「在官方允许的样例数据 + 公开数据集上做转导蒸馏 + 纯监督学习」。**

### 2.2 关键洞察：转导（transduction）是主分量的唯一引擎

复赛**提供了 20000 张无标签测试图**。我们让教师模型对这 20000 张打**软标签**，再训练一个学生去拟合 —— 即标准的**测试集转导蒸馏**。

**这是整套方案里贡献最大的一步**（初赛中 `cliph_rerun` 单独就 ≈0.9125 AUC，比历史 anchor 线更高）。

同时我们通过一组对照实验，把这条路的**边界**也量化清楚了：

| 分量 | 训练数据 | 与 `cliph_rerun` 的 ρ |
|---|---|---|
| `cliph_rerun`（主分量） | 测试集 20000 **软标签** + 样例 800 硬标签 | 1.0 |
| 只换教师（4 epoch） | 同上 | 0.9759 |
| 只换教师（8 epoch） | 同上 | 0.9786 |
| 转导 + 完整 Tiny 硬标签（占训练权重 57%） | 软 + 31369 硬 | 0.9315 |
| **纯监督（无教师软标签）** | 302k 硬 | **0.7785** |
| **纯监督（换骨干）** | GenImage++ 78k 硬 | **0.7914** |

**规律**：只要训练集里有「测试集 20000 张 + 教师软标签」这一路，学生就必然与教师高度相关 —— **那 20000 张就是被评估的那批图本身**。无论再掺多少其他数据，模型在测试集上的排序都由「拟合教师」主导。

⇒ **转导蒸馏的价值在「复刻」而不在「多样」**，它天然适合当**主分量**；
   而想要「独立信号」，**必须走纯监督 + 换骨干/换数据**。

### 2.3 关键洞察：独立 ≠ 有用，**强度才是决定性的**

历史上我们四次尝试「往主分量里加独立分量」，**四次全部掉分**。

最终定位到判据是**两个条件必须同时满足**：

```
独立（与主分量 ρ 足够低）  AND  自身足够强（单独 AUC 接近主分量）
```

| 注入源 | 与主分量 ρ | 单独强度 | 注入 20% 的实测/推算结果 |
|---|---|---|---|
| `nprft` | 0.12 | ~0.61 | ❌ −0.0017 |
| `align` | 0.73 | ~0.82 | ❌ 崩 −0.082 |
| `cliph300k` | 0.7785 | **~0.826** | ❌ −0.0035（净亏） |
| **`gpp`** | **0.7914** | **0.9054（LB 实测）** | ✅ **+0.0015** |

`cliph300k` 的单独强度是这样反解出来的：它在样本上的探针 val 高达 **0.9931（全场最高）**，但作为主分量整槽替换时 LB 掉了 **0.0416** —— 由这个干净的单变量差反解得其真实 AUC 仅 **≈0.826**，**sample val 虚高了 17 个点**（初赛样例与复赛测试集分布差异过大）。

⇒ **「低相关但极弱」的分量是负贡献**；只有「低相关且强」才值得押。这条判据直接决定了最终配方。

**训练配置**：

| 项 | 值 |
|---|---|
| 骨干 | `open_clip` CLIP ViT-H-14（`laion2b_s32b_b79k`，632M 参数，冻结） |
| 适配器 | LoRA，`r=32`，`lora_alpha=32`（scaling=1.0），dropout 0.05 |
| target_modules | `q_proj, k_proj, v_proj, out_proj, c_fc, c_proj` |

### 3.4 尺寸先验（统计分量）

**观察**：AI 生成器输出尺寸相对固定，真实照片尺寸多样。

| 尺寸 | 假图率（样例 1000） | 测试集占比 |
|---|---|---|
| 512×512 | 92.2% | — |
| 1024×1024 | 83.0% | 11.3% |
| 1280×720 | 67% | 6.1% |
| 1024×576 | 56.0% | 11.5% |
| 1024×768 | 16.9% | 7.4% |
| 1024×683 | 6.9% | 6.5% |

**构造**（两级互补，5-fold CV 选权重）：
```
prior_A = 尺寸档查表（贝叶斯收缩： (mean·n + 全局均值·5) / (n + 5) ）    OOF 0.8189
prior_D = GBM[w, h, ar, px, bytes, bpp, is_sq, short, long]              OOF 0.8195
prior   = 0.4·rank(prior_A) + 0.6·rank(prior_D)                          OOF 0.8247
```
与深度模型的相关仅 **0.146** ⇒ 「又强又独立」，是后融合的理想成分。

⚠️ **合规声明**：此项属 shortcut learning（利用数据集构建偏差而非生成痕迹）。按现行规则**不违规**（用的是官方允许的样例标注数据），但若赛题另有「仅基于图像内容判断」条款则可能踩线。**它绝不参与任何模型训练** —— 因为训练数据的尺寸分布与测试集差异大，投喂给模型会学到错误的先验；**只在最终后融合阶段使用**。

## 4. 融合策略

### 4.1 为什么用 rank 加权而不是分数加权

各分量输出的分数分布差异极大：

| 分量 | 分布特征 |
|---|---|
| `cliph_rerun` | 罕见的**饱满分布**（99.5% 落在 0.05~0.95） |
| `cliph300k` | **极度饱和**（42.6% > 0.99，28.2% < 0.01，中间段只剩 17.9%） |
| `gpp` / `bigg` | 居中 |

直接做分数加权会让**饱和分量把 70% 的图打成并列**，把排序权交给其余弱分量。
⇒ 必须先做 **rank 归一化**，再做线性加权，最后再取一次 rank 得到提交分数。

### 4.2 融合公式

```
slot_cliph = 0.20·R(rerun) + 0.20·R(s1) + 0.20·R(s2) + 0.20·R(s3) + 0.20·R(gpp)
slot_bigg  = 0.50·R(bigg2) + 0.50·R(bigg3)
slot_s384  = R(s384r)

base = 0.75·slot_cliph + 0.1429·slot_bigg + 0.1071·slot_s384
z    = 0.80·base + 0.20·R(prior)
score= rank(z) / (n+1)                       # R(x) = rankdata(x)/(n+1)
```

### 4.3 权重是怎么定下来的（全部基于 LB 实测的坐标上升）

| 轴 | 扫描点 | LB 实测 | 结论 |
|---|---|---|---|
| 主槽权重 c | 0.65 / **0.75** / 0.85 / 1.00 | 0.914498 / **0.916175** / 0.915787 / 0.91193 | 峰值在 **0.75** |
| 尺寸先验权重 w | 0.125 / 0.17 / **0.20** | 0.913422 / 0.915569 / **0.916175** | 峰值在 **0.20** |
| 主槽内 gpp 比例 α | 0.10 / 0.15 / **0.20** / 0.30 | （模型扫描） | 曲线在 0.30~0.45 很平，0.20 取保守值 |

**一个重要校准**：我们用 LB 实测点反解出**传导系数 k ≈ 0.326**
（主槽 AUC 增益 → 总分增益）。这说明「主分量再涨 0.003，总分才涨 0.001」——
**它直接解释了我们为什么到 0.919 就基本封顶**，也避免了大量无效的 GPU 投入。

### 4.4 把「批 rank」改写成「逐图可计算」—— Docker 化的核心难点

提交文件是**在 20000 张上排名**得到的，`rank` 是**批操作，单张图算不出来**。
Docker 服务必须逐张给出 score，两者不可能直接一致。

**我们的解法：把 `rank` 换成 `ECDF`（经验分布函数）**

```
R(x)  →  ECDF(x) = (searchsorted(sorted_ref, x, 'left')
                  + searchsorted(sorted_ref, x, 'right') + 1) / 2 / (n + 1)
```

- 参考表 = 该分量在 20000 张测试图上的**升序分数表**（每张表仅 160 KB）
- 在测试集上 **ECDF ≡ rankdata(method='average')/(n+1)**（逐位相等）
- 对新图是**良定义的单调映射**（等价于「用测试集分布做分位数标定」）

**实测**：逐图管线重算 20000 行 vs 提交文件 → **spearman = 1.0000000000**（AUC 完全相同）。

⚠️ 公式里那个 `+1` 不能少：少掉就恒小 `0.5/(n+1)`。对并列组大的量（尺寸先验只有 43 个档位）
这个常数偏移会让查询值落到并列组的**另一侧**，凭空产生 ~3.5e-3 的跳变。
我们用逐层比对（档查表 → GBM → 混合 → ECDF）把它定位出来 —— 残差恰好等于「并列组大小/(n+1)」。

## 7. 局限性与合规声明

1. **转导性质**：8 个分量里有 4 个是「用测试集软标签蒸馏」的学生。
   它们在这 20000 张上的表现**不代表对新数据的泛化能力** —— 这是转导学习的固有性质，
   也是我们在复赛允许无标签测试集的规则下所采用的合法手段。
2. **尺寸先验的合规边界**：属 shortcut learning。按现行规则不违规，但若赛题另有
   「仅基于图像内容判断」条款则可能踩线 —— **提交前请确认规则**。
3. **Docker 服务的已知偏差**：服务是**逐张**推理（BS=1），而冻结 CSV 由 **BS=32** 批量产出。
   bf16 下的数值抖动会让极少数图偏移（`--http` 验证的 spearman 预期 ≥0.99）。
   这是 HTTP 单图服务无法避免的，**不影响量级**。
4. **我们未能突破的天花板**：主分量受「转导学生不超过教师」约束（教师 AUC ≈0.9133，
   学生已达其 99.91%），加上传导系数 k≈0.326，**本方案的结构性上限约在 0.919~0.920**。
   我们尝试过 7 个方向（更大数据、更大骨干、更高分辨率、更强教师、更多 seed、
   多源注入、现成开源检测器），**全部被实验否证**。

## 8. 结论

本方案在**不依赖任何外部检测器、不违反规则**的前提下，把 LB 从 0.908114 提升到 **0.918887**。

三条最有价值的经验：

1. **转导蒸馏是主分量的唯一有效引擎，但它天生带来高相关** —— 高相关是它的**特性**（适合当主分量），不是缺陷；
   想要独立信号必须另起炉灶（纯监督 + 换骨干/换数据）。
2. **判断一个分量能不能用，看的是「强度 × 独立性」两个条件同时成立** ——
   我们曾四次被「低相关」误导，直到把每个分量的**真实强度反解出来**（而不是看样本 val），
   才发现 `cliph300k` 的 val 虚高 17 个点。**样本 val 不能预测测试集 LB。**
3. **唯一可信的裁判是排行榜本身** —— 我们把每一次提交都设计成**单变量对照**，
   并用实测点反解出传导系数 k≈0.326，从而在后期不再浪费算力去追不存在的增益。

## 9. Docker 交付实现

### 9.1 最大的技术难点：**`rank` 是批操作，单张图算不出来**

提交文件是**在 20000 张测试图上做 rank 加权**得到的，而 Docker 服务必须对**单张图片**给出 score。
两者不可能直接一致。

**解法：把 `rank` 换成 `ECDF`（经验分布函数）**

```
rk(x) = rankdata(x) / (n+1)
   ↓
ECDF(x) = ( searchsorted(ref, x, 'left') + searchsorted(ref, x, 'right') + 1 ) / 2 / (n+1)
```

- 参考表 = 该分量在 20000 张测试图上的**升序分数表**（8 张表共 0.4 MB，打进镜像）
- 在那 20000 张上 **ECDF 恒等于 `rankdata(method='average')/(n+1)`**（逐位相等）
- 对新图是**良定义的单调映射**（等价于「用测试集分布做分位数标定」）

**实测：逐图整链重算 20000 行 vs 提交文件 → `spearman = 1.0000000000`（AUC 完全相同）。**

> ⚠️ 公式里那个 `+1` 不能少。少掉就恒小 `0.5/(n+1)`；对**并列组大**的量（尺寸先验只有 43 个档位）
> 这个常数偏移会让查询值落到并列组的**另一侧**，凭空产生 ~3.5e-3 的跳变。
> 我们用逐层比对（档查表 → GBM → 混合 → ECDF）定位出来，残差**恰好等于「并列组大小/(n+1)」**。

### 9.2 尺寸先验的逐图化

`size_prior2` 的构造被完整固化进镜像（`bucket.json` + `gbm.pkl`）：

```
prior_A = 尺寸档查表（贝叶斯收缩：(mean·n + 全局均值·5)/(n+5)）        ← 只用 (w,h)
prior_D = GBM[w, h, ar, px, bytes, bpp, is_sq, short, long]           ← bytes = 图片字节数
prior   = 0.4·ECDF(prior_A) + 0.6·ECDF(prior_D)
```
两者都可逐图计算，**且已验证逐位复现 `size_prior2.csv`（max|Δ| = 0.000e+00）**。

### 9.5 构建方式（OCI 手法，无需 Docker daemon）

交付环境是一个**无特权容器**（`CapEff` 无 `cap_sys_admin`），实测：
`docker build` → `unshare: operation not permitted`；
`docker pull` → `failed to register layer: unshare: operation not permitted`（换 vfs 存储驱动同样失败）。

因此我们改用 **`skopeo` + 手工 OCI 布局**组装镜像（`skopeo` 只做"下载 + 解 tar"，不碰命名空间）：

```
skopeo copy docker://<官方基座> oci:base_oci      # 拉基座
  ↓ 追加一层：app/（代码+权重+骨干+查表） + pip 补装依赖 + appuser
  ↓ 写 OCI 布局（config / manifest / index）
skopeo copy oci:final_oci docker-archive:image.tar   # 产出合规的 docker save tar
```

产出的 tar 是标准的 docker-archive：`manifest.json`（`Config` + `RepoTags` + `Layers`）
与 7 个以 **`<diff_id>.tar`** 命名的层成员，`arch=amd64`，可直接 `docker load`。

> **验证纪律**：手工组装没有 Docker 帮我们兜底，所以每一步都要能被独立验证。
> 交付前的最后一道是 —— 把**成品 tar** 解成一个 rootfs，用 `chroot` 代替 `docker run`，
> **以最终运行身份 `appuser`** 把 `/app` 下每个文件 `open()` 一遍并启动服务；
> 脚本就是 `docker_submit/verify_container.sh`（不需要 Docker，也不需要 GPU）。
> 之所以能这么做：构建机虽然没有 `CAP_SYS_ADMIN`（`unshare` 被拒），但 **`chroot` 只需要
> `CAP_SYS_CHROOT`**，所以"真的把镜像摊开、真的在里面跑"是可行的。

> 同时提供了标准的 `Dockerfile`（同样的基座、依赖、探针、非 root、`EXPOSE 8080`、`HEALTHCHECK`），
> 在有 Docker 的机器上 `docker build` 可得到等价镜像。

### 9.6 组装脚本自身的三次返工（**每一次都是"自检"抓出来的**）

OCI 手法要手写组装脚本，风险比 `docker build` 高得多 —— 因为**没有 Docker 帮我们检查**。
下面三次返工都发生在**交付前**，记录了自检是怎么起作用的，也说明为什么每一步都要能被独立验证。

| # | 问题 | 为什么危险 | 修法 |
|---|---|---|---|
| 1 | **三个骨干一个都没进层** | 组装脚本里 `cp -al <骨干> layer2/app/backbones/<名字>` **忘了先 `mkdir backbones`**，`cp` 报 `No such file or directory`，而**返回值没有被检查** ⇒ 层只有 1.47 GB（应为 ~12 GB），镜像却"组装成功"。这样的镜像跑起来必然找不到骨干权重 | ① 先 `mkdir -p`；② **每次 `cp` 都检查 `returncode`，失败即 `sys.exit`**；③ 加**硬断言**：骨干**文件数与总字节数**必须与源目录逐一相等，否则拒绝继续；④ 再加一道"整层 < 5 GB 就报错"的兜底 |
| 2 | **融合表自检跑在宿主 python 上** | 自检本意是"验证容器里能加载查表"，但它用的是宿主机的 `python3`（scikit-learn 1.9.1），于是报了一个**容器里根本不会发生**的 `ModuleNotFoundError: No module named '_loss'` —— 自检**测的是宿主机，不是镜像** | 改为用 `PYTHONPATH=<piproot>` **子进程**跑自检，复刻容器的包集合；并在输出里打印 `sklearn / numpy / python` 版本，让"在哪个环境验的"一目了然 |
| 3 | **`piproot` 被 `shutil.move` 搬走** | 依赖目录被"搬"进层里，层一删就没了 ⇒ **每次重跑都要重装一遍依赖**（第一次重跑就白白触发了那条要 20 分钟以上的慢路径） | 改成 `cp -al`（硬链接）：几乎不占额外空间，且 `piproot` 原样保留，重跑直接命中"跳过安装"分支 |

关于**依赖版本**，有一条值得单独说明：

> `app/tables/gbm.pkl`（尺寸先验的 GBDT）是用 **scikit-learn 1.6.1** 序列化的。
> 我们实测：把它分别载入 **1.6.1** 与 **1.7.2**，对同一固定随机矩阵的 `predict_proba`
> 输出**逐位相同**（`mean/min/max` 与逐元素前若干位全等，字节级差异仅来自 numpy 的
> SIMD 求和核，量级 ~1e-16）。
> 由于融合全程走 **ECDF（纯 rank 变换）**，1e-16 的扰动不可能改变任何一张图的排序。
> 尽管如此，镜像里**仍把 scikit-learn 钉在 1.6.1**（与序列化它的版本一致），
> 以消除 `InconsistentVersionWarning` 并保证与冻结产物完全同源。

**组装脚本的迭代产物也一并交付**（`oci_tools/`）：`pip_explicit.py`（`--no-deps` + 42 个显式包，
绕开 pip 在 cross-platform 模式下 20 分钟以上的回溯）、`verify_on_host.py`（**用真实测试图跑完整链路**
并与冻结 CSV 逐图比对 spearman）、`run_final.sh`（全流程编排）等。

> **关于 `img_bigg_s384_retrain`（spearman 0.9726，最终权重 10.714%）——如实说明，并给出它对最终分数的影响：**
>
> 这一格**确实被用到**（`fusion_meta.json` 里的第三槽，槽权重 `0.107142857` × 槽内 `1.0`）。
> 我们在**最终分数空间里**做了精确消融：用交付包自身的 ECDF 查表把 `fused` 反解回 `z`，
> 再只把这一格替换成冻结 CSV（其余 7 个分量、尺寸先验、所有权重全部不动）：
>
> | 变体 | spearman vs 提交文件 |
> |---|---|
> | 现状（镜像算的 8 个分量） | **0.999508** |
> | 只把这一格换成冻结 CSV（"若它完美"） | 0.999891 |
> | **⇒ 这一格带来的差距** | **+0.000382** |
>
> **即：它的偏差只让融合排序一致度从 0.9999 降到 0.9995，对最终 AUC 的影响可以忽略。**
>
> 已逐项核对并**排除**了以下原因：预处理（`Resize((384,384), BICUBIC)` + CLIP 归一化、
> `interpolate_pos_encoding=True`、`lora_alpha=2r` ⇒ scaling 2.0）与该分量训练脚本
> `train_s384_sj.py` **完全一致**；权重与分量名也**没有错配**（该分量最像的冻结 CSV 仍是它自己）；
> 并且用**完全复刻训练侧**的配置（fp32 权重 + `autocast(bfloat16)`）单独重跑，
> 结果 **0.965585 vs 服务侧 fp16 的 0.965432 —— 两者一致**，说明**不是精度问题**。
> 结论：我们打包的这份 LoRA 与产出该冻结 CSV 的那份 `best.pt` **是同配方下的两次不同训练**，
> 而原始 run 目录位于已释放的实例盘、**无法再取回**，因此这一项无法进一步收敛。
> —— 我们把这条差异主动写进报告，而不是把它藏在一个"通过"的结论后面。
