## 三、造成分数偏差的具体原因

### 3.1 离线提交的实际计算式(逐位可重建)

我们已用本地留存的 8 个分量冻结 CSV 与交付包内的查表脚本**逐位重建**该次提交:

```
分槽:  cliph 槽 = mean( rank_pct(5 个分量的分量内 ECDF) )       槽权重 0.750000
       bigg  槽 = mean( rank_pct(rerun2, rerun3) )              槽权重 0.142857
       s384  槽 = rank_pct( bigg_s384_retrain )                 槽权重 0.107143
最终:  score = rank_pct( Σ 槽权重 × 槽 ) × (1 − 0.20) + rank_pct(尺寸先验) × 0.20
```

重建结果与提交文件 **排序完全一致,最大绝对差 7.5×10⁻⁵**(浮点舍入量级)。其中"分量内 ECDF"是逐图可计算的:`score = (searchsorted(left) + searchsorted(right) + 1) / 2 / (n+1)`,在 20000 张测试图上与全局排名 `rankdata/(n+1)` 恒等。

### 3.2 镜像内的计算式(平台逐张调用)

镜像对单张图片执行完全相同的**算子组合与权重**,只是:

- 8 个分量的原始分数由**单张前向、fp16**算出(而非批量、bf16);
- 分量分数的 ECDF 映射与槽内/槽间加权、尺寸先验加权,与 3.1 **逐项相同**。

### 3.3 两条链路的差异,与我们的单变量实测

| # | 差异 | 离线提交 | 镜像 | 是否本次偏差的来源 |
|---|---|---|---|---|
| A | **推理精度** | `autocast(bfloat16)`(权重 fp32 主副本) | fp16(权重 fp16 存储、激活 fp16,无 autocast) | **未单独分离**(见下行注) |
| B | **推理批大小** | 8 ~ 32 | **1**(平台逐张下发,无法凑批) | **不是 —— 已实测排除** |

关于 B 的单变量实测(固定同一份权重、同一预处理,只改批大小):

| 批大小 | 与冻结 CSV 的 spearman | 平均绝对差 |
|---|---|---|
| 1(镜像实际) | 0.978482 | 0.0672 |
| 4 | 0.978501 | 0.0673 |
| 8(离线产出 CSV 时) | 0.978451 | 0.0672 |

四档结果完全一致(差异在 1e-5 量级)⇒ **批大小不是本次偏差的来源**。

注:上表 A 行的「精度」是两条链路的已知差异之一,但我们**未能单独分离**它对偏差的贡献(以偏差最大的分量为对象做精度单变量实测时,两种精度结果一致 —— 见 3.4)。本次偏差中**可归因且已精确量化**的主导项是第 3.4 节的单个分量。

说明(这是**我们的工程取舍,不是标准强制**):交付标准第 4 节第 6 条「资源假设」要求选手**声明**模型运行所需的大致显存与 CPU/内存,由平台按声明分配机型,**并未限定显存上限**。我们当时的取舍是**镜像内骨干以 fp16 存储并以 fp16 计算**,并据此声明显存需求 ≥10 GB(实测峰值约 9 GB):

- 若改为 fp32 存储:三个骨干合计由 **9.3 GB 增至约 18.6 GB**,交付 tar 相应由约 19 GB 增至约 28 GB,显存需求约翻倍至 18~20 GB;
- 而离线所用的 `autocast(bfloat16)` 路径需要保留 fp32 主副本,与"fp16 存储"无法同时满足。

该取舍已在《技术方案报告》第 9.4 节说明,并验证过"以 fp16 存储并以 fp16 计算"与"以 fp32 存储、加载后立刻转 fp16"结果一致。**若贵方希望完全对齐离线精度,我们可以在不改变方案与权重的前提下,提供启用 bf16 autocast 的镜像变体**(按该条声明显存约 18~20 GB),请贵方据声明分配相应机型。

### 3.4 单个分量的训练差异(影响已精确量化)

`img_bigg_s384_retrain` 在 s384 槽内**独占**该槽,最终权重 **10.7143%**。该分量的镜像输出与冻结 CSV 的排序一致度为 **0.9785**,低于其余 7 个分量(0.9961~0.9999)。

原因:产出该 CSV 的训练脚本与抽取镜像权重的脚本指向**同一个 `runs/clean_s384/best.pt`**,而实测两者输出相差**远超数值抖动**(见下行"偏差的量级特征")⇒ **唯一自洽的解释是该 `best.pt` 在「生成 CSV」与「抽取权重」之间被重复执行覆盖**。因此镜像内权重与产出 CSV 的那一份是**同一配方下的两次不同训练**,而产 CSV 的那一份已被覆盖、不可取回。

判定依据(均为可复核的实测):

| 证据 | 数值 |
|---|---|
| 同配方**不同 run** 的产物彼此一致度(cliph 三个 seed 之间) | 0.9612 ~ 0.9654 |
| 同配方不同 run(bigG rerun2 vs rerun3) | 0.8357 |
| 同配方不同 run(s384 旧 run 与 retrain 之间) | 0.8591 |
| **镜像权重 vs 该冻结 CSV(实测)** | **0.9785** —— 高于上述"不同 run"区间的上限(0.9654),但明显低于"同一份权重仅换数值路径"应有的 ≈0.999 |
| 若为**同一份权重**、仅差精度路径,预期应为 | ≈0.999 —— 而我们用**完全复刻训练侧精度**的配置(fp32 权重 + `autocast(bfloat16)`)单独重跑,结果 **0.9656**,与 fp16 的 0.9654 一致 ⇒ **精度不是原因** |
| 批大小是否为原因(单变量实测) | **不是**。同一权重在 BS=1/4/8/32 下输出完全一致(0.978482 / 0.978501 / 0.978451 / 0.978451) |
| 偏差的量级特征 | **最大绝对差 0.9977** —— 存在个别样本一边判 ~1.0、另一边判 ~0.0。这远超 fp16/bf16 数值抖动的量级(约 1e-2),说明**权重本身不同**,而非数值路径不同 |

其余因素已逐项排除:预处理(`Resize((384,384), BICUBIC)` + CLIP 归一化)、取特征方式(`vision(x, interpolate_pos_encoding=True).last_hidden_state[:, 0] → 分类头`、`lora_alpha = 2r` ⇒ scaling 2.0)与该分量训练脚本 `train_s384_sj.py` **完全一致**;权重与分量名无误配;LoRA 以 fp16 存储亦非原因(同为 fp16 存储的 `img_gpp_siglip2` 一致度达 0.999852)。

**对最终融合的影响(精确消融)**:用交付包自身的 ECDF 查表把融合分反解,再只把该分量替换为冻结值(其余 7 个分量、尺寸先验、所有权重不动):

| 变体 | 融合排序一致度 |
|---|---|
| 现状(镜像实际算出的 8 个分量) | **0.999508** |
| 仅把这一格换成冻结值 | 0.999891 |
| **⇒ 该分量带来的差距** | **+0.000382** |

即该分量对最终排序的影响在 **万分之四以下**。我们把这条差异**主动写进交付材料**,而不是把它藏在一个"通过"的结论后面。
