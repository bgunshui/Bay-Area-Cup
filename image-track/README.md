## 2. 方案总览

### 2.1 架构：3 骨干 × 8 分量 → 三槽 → 尺寸先验

```
                   ┌─ cliph 槽 (0.750000) ────────────────────────────┐
                   │   img_cliph_rerun       0.20  ← 转导蒸馏（占基底 42.25%）│
                   │   img_cliph_s20261101   0.20                      │
 输入图片 ──┬─► 3 个骨干 ─┤   img_cliph_s20261102   0.20                      │
（单张）    │   × LoRA   │   img_cliph_s20261103   0.20                      │
            │            │   img_gpp_siglip2       0.20  ← SigLIP2+GenImage++ │
            │            └──────────────────────────────────────────────┘
            │            ┌─ bigg 槽 (0.142857) ─┐
            │            │  img_bigg_rerun2  0.5│  ← bigG@224
            │            │  img_bigg_rerun3  0.5│
            │            └──────────────────────┘
            │            ┌─ s384 槽 (0.107143) ─┐
            │            │  img_bigg_s384_retrain │  ← bigG@384, r=32
            │            └──────────────────────┘
            │
            └─► 尺寸先验 (0.20) ← 从官方初赛样例 1000 张学（OOF AUC 0.8247）
```

**最终分数**（逐图可计算）：

```
score = rank_pct( Σ 槽权重 × 槽 )  × (1 − 0.20)  +  rank_pct( 尺寸先验 ) × 0.20
其中槽内 = mean( rank_pct( 各分量的分量内 ECDF ) )
```

| 骨干 | 参数量级 | 用途 |
|---|---|---|
| CLIP **ViT-H-14**（open_clip） | ~1.0 B | cliph 族 5 个分量的共享骨干 |
| CLIP **ViT-bigG-14**（HF） | ~2.5 B（含文本塔） | bigg 槽 2 个 + s384 槽 1 个 |
| **SigLIP2-so400m-384** | ~0.9 B | gpp 分量 |

> 8 个分量**共享 3 个骨干**，各自只挂 LoRA + 分类头（每个 ≈100 MB）⇒ 显存与镜像体积可控。

### 2.2 为什么这样设计（一句话一条）

| 设计 | 理由 |
|---|---|
| **LoRA 而非全量微调** | 8 个分量共享骨干，全量微调要 8 份权重（~80 GB） |
| **多骨干多视角** | 不同骨干对同一扰动的敏感方向不同 ⇒ 天然互补 |
| **主槽用转导蒸馏** | 把"整个混合的排序"去噪成一个**图像可计算的函数**（高相关是特性，不是缺陷） |
| **往主槽注入独立分量** | 基底与主分量相关 0.9758 ⇒ 只有往主槽里注入才能改变结果 |
| **尺寸先验后融合** | 尺寸分布与生成痕迹无关；**不投喂模型**，避免把外部数据的错误先验学进去 |

## 5. 复现（不需要 GPU、不需要权重）

```bash
cd code/docker_submit

# ① 建环境（约 1 分钟，只装 4 个小依赖，不装 torch）
python -m venv .venv
.venv/bin/pip install -r requirements-verify.txt      # Windows: .venv\Scripts\pip

# ② 逐图重建提交文件
.venv/bin/python verify_reproduce.py --from-csv       # Windows: .venv\Scripts\python
#    → 必须输出 spearman = 1.0000000000
```

这条命令只读 `submission/` 里的 10 个 CSV + 镜像内的查表，**逐图重建 0.918887 的提交文件**。
脚本会**自动定位** CSV 目录（交付包内 / 本仓库内两种布局都能跑）。

> **⚠️ 环境要求（实测踩过）**：`app/tables/gbm.pkl` 是用 **numpy 2.x** 序列化的，
> **numpy 1.x 读不了**（报 `No module named 'numpy._core'`，与业务无关）。
> 用 numpy<2 跑会看到一屏看不懂的报错 —— 脚本现在会**提前拦住并给出解法**。
> 另外 `gbm.pkl` 由 **scikit-learn 1.6.1** 序列化、镜像里是 1.7.2，
> 加载时会有一条 `InconsistentVersionWarning`，**已实测不影响结果**。
> Windows 控制台若中文乱码，先执行 `chcp 65001`。

需要跑真实服务时：`bash code/docker_submit/verify_container.sh <镜像 tar>`（**需 Linux；没有 Docker 守护进程也能跑**，
脚本用 chroot 代替 `docker run`，逐层摊开镜像后以非 root 用户启动服务并打三探针）。

> **本仓库副本与冻结交付包的差异（如实说明）**：`code/docker_submit/verify_reproduce.py`
> 比交付包里那一份多了三处**向后兼容**的改动 ——
> ① CSV 目录自动定位（冻结版假定 CSV 平铺在包根，在仓库布局下会 `FileNotFoundError`）；
> ② numpy<2 环境闸门；③ stderr 也设为 UTF-8。**其余脚本与 `app/` 下的服务代码逐字节相同。**

## 6. 如实披露（评审必问，先看这里）

| # | 事项 | 说明 |
|---|---|---|
| 1 | **转导性质** | 8 个分量里 4 个（cliph 族）是"用测试集软标签蒸馏"的学生 ⇒ **在这 20000 张上的表现不代表对新数据的泛化能力**。这是刻意的转导设计，已写进报告与提交说明 |
| 2 | **尺寸先验属 shortcut learning** | 利用的是数据集构建偏差（生成器输出尺寸固定）。按现行规则不违规（用官方允许的样例标注），但已**主动披露**；它占最终权重 20% |
| 3 | **单分量 checkpoint 差异** | `img_bigg_s384_retrain` 与产出其冻结 CSV 的权重是**同一配方下的两次不同训练**（原文件被覆盖）；该项对最终排序影响 **+0.000382** |
| 4 | **镜像与离线的数值路径不同** | 离线 bf16 autocast + 批推理；镜像 fp16 + 单张。批大小已实测排除；精度项未单独分离（已在给组委会的说明中如实写明） |
| 5 | **工程事故与修复** | 首版镜像曾因"骨干文件权限 0600 而容器以非 root 运行"导致加载失败；另有基座不含 `curl` 导致 HEALTHCHECK 永假。两者均已修复并做了独立复检（见 `docs/03`） |
